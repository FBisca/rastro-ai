# Plan: Claims and `about`

Slug: `claims-and-about`. Living spec: `docs/specs/claims.md` (new; `docs/specs/evidence.md` and `docs/specs/surfaces.md` amended). Status: APPROVED 2026-11-04. Paused 2026-11-04 for the knowledge graph discussion; resumed 2026-11-05 by the owner after the deep dive (see Pause, resolved, and "Amended 2026-11-05" in Decisions).

## Why now
Roadmap slice 3. Slice 2 lets the owner's agents `search` evidence over MCP. Search hands back text, though, and "text alone is never knowledge" (concept §1). This slice derives the first **claims**: observed only, from structured GitHub evidence. It adds two reads on both surfaces, `about(entity)` and `why(claim)`, and every claim traces back to its evidence. Slice 4 (a second source, one identity) builds merges on the entity and alias model laid down here.

Real data today: 1520 evidence rows. The only structured field is `/state` (405 closed, 1 open), and authors were never captured. Without the connector change and a re-read, `about(<account>)` would come back nearly empty.

## Scenarios
**Connector and re-read**
- **S1** WHEN the GitHub connector reads a PR, issue or comment with an author, THEN it submits `structured` evidence at `/user/id`, `/user/login` and `/user/type` at that item's location; WHEN the author is null, THEN it submits no author evidence.
- **S2** WHEN `rastro sync <source> --reread` runs, THEN the connector reads from the registered window start: unchanged fields add no evidence, new fields append, coverage is recorded as for any sync, and an item that isn't returned changes nothing.

**Extractor protocol and validation**
- **S3** WHEN a sync accepts evidence for a source bound to an extractor, THEN the extractor runs over that (source, scope)'s pending evidence, its claims can be read through `about` and `why`, and the extractor run is logged as its own run with plugin id, version and counts; the source's coverage is the same as without the extractor.
- **S4** WHEN an extractor submits a claim whose support is untrusted evidence, evidence not delivered to that run, a span outside its evidence, or a rule not declared deterministic, THEN the core records nothing for that claim and counts it rejected.
- **S4a** WHEN a submitted claim's predicate isn't in the vocabulary, or its subject or object breaks the predicate's domain or range, THEN it's rejected and counted.
- **S4b** WHEN one span of a claim's support bundle fails a check, THEN the whole claim is rejected and counted, even though its other spans pass.
- **S4c** WHEN a submitted claim has an endpoint whose type isn't given by a `rastro:type` claim in the same submission, THEN it's rejected and counted, even if an earlier submission typed that entity; WHEN a submission's `rastro:type` disagrees with a type from another submission and neither is a `supertype` of the other, THEN both stay visible as a conflict.
- **S5** WHEN a source's bound extractor isn't installed, THEN the sync succeeds and `about` reports extraction state `not_installed` for that pair; WHEN an extractor is installed but not bound to the source, THEN it never runs.
- **S6** WHEN an existing GitHub source is loaded, THEN it is bound to `rastro-extractor-github` without the owner editing config.

**Claims, identity and time**
- **S7** WHEN two sources observe the same PR with the same state, THEN there is one PR entity and one `code:state` claim with two supports.
- **S8** WHEN a second support arrives for an existing claim, THEN the claim id stays the same and the revision changes.
- **S8a** WHEN the same evidence is replayed into a fresh database (other local evidence ids), or the bound extractor's version changes without changing a claim's visible state, THEN the claim's id and its `rastro/revision/v2` revision are unchanged.
- **S9** WHEN a PR's state goes open → closed → open, THEN the `open` claim keeps its id, is `superseded` and then `observed` again with a new revision; `why` shows both known intervals; the `closed` claim is `superseded` with `superseded_by` pointing at the `open` claim.
- **S9a** WHEN a PR's state is observed open, then closed, then open, all at the same `captured_at`, THEN `why` shows two separate occurrences of the `open` claim and one of the `closed` claim, ordered by event key and allowed to be zero-length, and the `open` claim is `observed`.
- **S10** WHEN a later observation lacks a field, has it null, or the item wasn't returned, THEN no claim is superseded.
- **S11** WHEN two sources' current observations of the same PR state disagree and one is newer and comparable, THEN the newer is current and the older is `superseded`; WHEN they tie or can't be compared, THEN both stay `observed` with `conflicts_with`.
- **S11a** WHEN one rule derives two claims from the same span (a repository and a kind from one URL), THEN both are stored, each with its own justification, and neither replaces the other.
- **S12** WHEN a claim is derived, THEN its known interval starts at the establishing evidence's `captured_at`, ends at the replacing evidence's `captured_at`, and its valid time reads `unknown`.
- **S13** WHEN an account's login changes between observations, THEN it stays the same entity, typed `code:Account` by a `rastro:type` claim, with both logins as `rastro:alias` claims whose known intervals show when each held; WHEN `/user/type` is `Bot`, THEN its `rastro:type` claim is `code:Bot`; no entity is typed `Person`, and no type is stored as a column or updated in place.
- **S14** WHEN a title or body holds instruction-like text, THEN no claim or display name comes from it.

**GitHub extractor and vocabulary**
- **S15** WHEN `rastro-extractor-github` processes the GitHub fixture, THEN it emits `code:state`, `code:author` and `code:in_repository` claims (with their `rastro:type` claims), each cited at the right field and span, with author and alias claims justified by one bundle of all the spans they need, and the core loads its `code` vocabulary, which has every required definition field and a `cardinality` on every predicate.
- **S15a** WHEN a vocabulary file has an unknown field, a predicate without `cardinality`, or a name under the core's `rastro:` prefix, THEN the core refuses to load it with an error naming the problem, and no claim is accepted under it.
- **S15b** WHEN a record's changed field reaches the extractor, THEN the core also delivers the companion fields of the same source, scope and location with evidence no newer than the batch's high-water mark, and a rebuild delivers the same set.

**Rebuild and failure**
- **S16** WHEN `rastro claims rebuild` runs after a series of incremental syncs, THEN the projection (entity and claim ids, revisions, statuses, supports, intervals) equals the incremental one, for a GitHub source and for a scripted (non-GitHub) source alike.
- **S16a** WHEN the bound extractor's version changes, THEN the next sync replays its pairs, reads serve the old version's claims until that replay completes, and then the new version's justifications replace the old ones in one transaction.
- **S16b** WHEN a rebuild or a sync's extraction publishes the projection, THEN one `projection_publication` row records the extractor and vocabulary versions and the evidence high-water mark, that row can't be updated or deleted, and the projection tables have fresh `ANALYZE` statistics.
- **S17** WHEN a sync fails after accepting some evidence, THEN the next writing sync extracts that evidence, even if it accepts nothing new.
- **S18** WHEN the extractor crashes or fails during a sync, THEN `sync` exits non-zero, the source's coverage stays as read, extraction state reads `failed`, reads serve the last good projection, and the next sync resumes from the checkpoint.
- **S18b** WHEN the replay for a new extractor version fails, THEN the old version's claims stay readable and unchanged, and extraction state reads `failed`.
- **S18a** WHEN an extractor run was left unfinished, THEN the next writing open marks it interrupted without creating a source coverage window.
- **S19** WHEN `rastro claims rebuild` fails partway, THEN the previous projection stays readable and unchanged; WHEN a reader runs during a rebuild, THEN it sees either the old or the new projection, never a mix.

**`about`**
- **S20** WHEN `about` is called with an entity id, a canonical alias or an exact canonical URL, THEN it returns the current claims where that entity is subject or object, each with claim id, status, revision, predicate, subject and object aliases and a support count; WHEN called with any other form, THEN it returns an operation error naming the accepted forms.
- **S21** WHEN `since` is given, THEN only claims whose known interval started at or after it are returned, newest known time first, then claim id; `limit` defaults to 20, accepts 1–50, and `truncated` says more exist; WHEN `history: true`, THEN superseded claims are included.
- **S22** WHEN `about` names an unknown entity or one visible only through hidden scopes, THEN both return the same empty result with coverage.
- **S23** WHEN `about` or `why` answers, THEN it includes coverage for every visible (source, scope) pair and extraction state per pair and extractor version; WHEN evidence is pending extraction, THEN that pair reads `behind`.

**`why`**
- **S24** WHEN `why` is called on a claim, THEN it returns the claim with status, revision, known intervals, valid time, conflict and supersession links and the extractor, rule and vocabulary versions, plus at most `limit` supports with `truncated`; each support carries evidence id, source, scope, location, field, span, `captured_at`, `source_updated_at`, trust class and an excerpt that starts and ends on UTF-8 boundaries with clipping flags; the full quote appears only with `full`; each support names its justification kind, extractor and version and lists every span of its bundle.
- **S25** WHEN `why` gets an unknown or hidden-only claim id, THEN it returns the same operation error (`isError: true` on MCP).

**Surfaces and scopes**
- **S26** WHEN the schema is generated, THEN it includes `about` and `why` under v2, it equals the committed file, and the existing operations' schemas are unchanged.
- **S27** WHEN an MCP client lists tools, THEN exactly `search`, `coverage`, `about` and `why` appear, each read-only; WHEN the same `about` or `why` request runs as `rastro … --json` and over MCP, THEN the envelopes are equal; `claims rebuild` isn't exposed on MCP.
- **S28** WHEN `rastro mcp --scope personal` serves `about` or `why`, THEN resolution, aliases, types, statuses, revisions, conflict and supersession links, counts and extraction state are computed from personal supports only, before the limit; a claim supported in both scopes shows only its personal supports, and a visible claim isn't hidden by a work-only replacement.
- **S28a** WHEN `about` and `why` run under random sets of scopes, THEN each answer equals the answer from a projection rebuilt over only that scope set's evidence, and adding or removing evidence in a hidden scope leaves it unchanged.
- **S28b** WHEN the scoped-read benchmark runs (a 20k-claim hub in a 100k-claim database, cold and warm, two scope sets), THEN scoped `about` p95 is under 200 ms; otherwise a scope-set cache is added with exact recompute as the fallback, and a read past its work budget fails rather than returning a weaker answer.

## Out of scope

## Risks
- **Security:** an extractor is an untrusted process. The core validates every support id, trust class, span, rule and vocabulary term (S4, S4a), and an extractor reads only the evidence of sources bound to it (D21). No claim comes from untrusted text (S14). Scope filtering covers metadata, not only rows (S28). Rank or ordering across scopes may still leak timing, as slice 2's §21 accepted limit; a scope isn't an isolation boundary until slice 14.
- **Performance:** extraction is incremental per checkpoint; rebuild is O(evidence), fine at ~1.5k rows. `about` and `why` are bounded by `limit`. Each projection batch is one transaction, so a sync holds the write lock a little longer; WAL readers aren't blocked.
- **Migration:** new tables for the projection, checkpoints and extractor runs; evidence isn't rewritten. Existing GitHub sources get the extractor binding by default (S6). Old items need `--reread` to gain author evidence. The projection is disposable: dropping it and running `claims rebuild` restores it.
- **Rollback:** unbinding the extractor stops extraction; `about` and `why` then report `not_installed`. Dropping the projection tables returns the store to slice 2 behaviour. Author evidence stays; it's ordinary evidence.
