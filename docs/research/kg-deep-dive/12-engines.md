# Embedded knowledge-graph stores and engines

Checked **2026-11-04**. Research, not a decision. Every external link below was checked on that date; dates in tables are release/commit dates, not check dates. `?` means unverified, not unsupported. Size estimates are qualitative engineering estimates, not measured binary deltas. Repository activity is evidence of maintenance, not a support commitment.

## Constraints and important corrections

- Rust library first; macOS/Linux required, Windows wanted (`docs/concept.md:45–60`; ADR 0001). A local server can be wrapped, but imposes process ownership and deployment work on library consumers.
- Current contract: SQLite, FTS5, separate read-only reader beside the writer, one snapshot per answer (`docs/adr/0002-sqlite-fts5-storage.md:8,22–33`). Claims are disposable generations, with deterministic identifiers, replay order and atomic activation (`docs/adr/0009-claims-projection.md:8–33`). Alternatives below would need owner-approved ADR changes.
- **The earlier “engine dying in 2026” description conflates dates.** Its Storage table identifies Kùzu, whose repository was archived **2025-10-10**, final release **0.11.3** that day. That is cessation of upstream maintenance, not removal of the MIT code. [Repository/archive notice](https://github.com/kuzudb/kuzu), [final release](https://github.com/kuzudb/kuzu/releases/tag/v0.11.3).
- There really is a **2026** death in this lineage: **Kineviz/Bighorn**, a Kùzu fork, archived **2026-10-23**; default branch last commit **2026-08-07**. Its archival reason is unverified. [Archive notice](https://github.com/Kineviz/bighorn), [commit feed](https://github.com/Kineviz/bighorn/commits/0.11.atom).
- LadybugDB explicitly describes continuing the archived Kùzu project; its March 2026 announcement includes security fixes and expanded bindings. RyuGraph and Vela also exist; a fork's existence is not proof of current maintenance. [Ladybug team](https://blog.ladybugdb.com/post/ladybug-spreading-its-wings/), [RyuGraph](https://github.com/predictable-labs/ryugraph), [Vela](https://github.com/Vela-Engineering/kuzu). Reports that Apple acquired Kùzu are widespread, but no first-party acquisition announcement was verified here; do not treat the reported buyer/cause as established.

## Transactions, retrieval, time and rebuild

`Application time` means Rastro stores explicit known/valid intervals; date datatypes, MVCC timestamps and database recovery are **not** bitemporal claim semantics. `G` and `E` refer to proposed rebuild patterns below, not existing Rastro implementations. All engine guarantees here are documentation claims; none was crash-tested in this research.

## Personal-scale fit: 10k–1M evidence rows, 100k–10M claims

**Estimate, not a benchmark result:** indexed SQLite is a credible baseline for bounded 1–2-hop queries at this scale. Total rows alone do not determine cost: seed count, degree skew, visible-support filtering, history multiplicity, sorting and output size do. One million evidence rows can also produce substantially more than ten million support/index rows. No checked source establishes a Rastro p95 latency at these sizes.

- Candidate indexes to measure: `(generation, subject, predicate, object)` and inverse object index; support indexes by claim/scope/current and evidence; interval indexes matching actual as-of predicates. Store typed identifiers in indexed columns; avoid traversing JSON-extracted fields. These are **proposals**, not changes to schema.
- Prefer a bounded join/union for exactly one or two hops; use recursive CTEs where variable depth is useful, with explicit depth/work/result bounds and cycle policy. A final `LIMIT` after sort/dedup need not bound the work. SQLite documents recursive queue evaluation and early termination behaviour. [WITH documentation](https://sqlite.org/lang_with.html).
- A published, reproducible **SQLite forum** test traverses a million-node decimal tree: recursive CTE **0.63s**, manually unrolled CTE **0.36s**, `NOT MATERIALIZED` **0.24s**. It sums **all descendants**, not a selective 2-hop neighbourhood, and is a user benchmark rather than an official performance guarantee. Useful evidence that query shape matters; invalid evidence for promising submillisecond Rastro reads. [Benchmark, schema and queries](https://sqlite.org/forum/info/016a25083a9f8eb5c6532ed5a961eb7c2362f667cbca305f65dccb2e82170df7?t=h).
- DuckPGQ's authors benchmark relational pattern matching and CSR path operations: useful evidence that relational tables plus graph-specific execution can compete on graph analytics; different datasets/hardware/workloads prevent direct extrapolation. [CIDR paper](https://vldb.org/cidrdb/papers/2023/p66-wolde.pdf), [VLDB demo](https://www.vldb.org/pvldb/vol16/p4034-wolde.pdf).
- Grafeo's graph-bench is **maintainer-run**, includes LDBC-inspired workloads, and is not an independent certification. Use its harness/query shapes as leads, not its “fastest” headline as the selection rule. [Harness](https://github.com/GrafeoDB/graph-bench).

**Proposed comparison gate:** run identical scoped `about`, `why`, search→two-hop, hub, cycle and historical queries at 100k/1M/10M claims, with warm/cold cache and simultaneous ingestion. Record p50/p95, visited rows, RAM, disk/WAL growth, rebuild duration/peak disk and reader latency during rebuild. Include sparse graphs and high-degree hubs; verify identical claims/supports/statuses before comparing speed. This research ran no database performance benchmark.

## Hybrid and rebuild patterns (proposals)

**G — same transactional store.** Existing ADR 0009 provides the reference: replay retained evidence in `(captured_at, evidence id)` order into a new generation; batch plus checkpoint atomic; activate generation atomically; retain old generation for active readers. Stable identifiers belong to Rastro, never to an engine's internal vertex IDs. Failed rebuild leaves previous generation readable. (`docs/adr/0009-claims-projection.md:19–33`.) SQLite/simple-graph can stay within this contract; a graph extension must prove its caches/indexes respect the same transaction and generation boundary.

**E — SQLite source of truth plus disposable engine.** Replay evidence/confirmations/rules into a new engine directory or database, with an immutable manifest containing generation, evidence high-water mark, extractor/vocabulary versions and checksums. Verify before activation. Pin both SQLite metadata and engine handle to that manifest for each answer; keep old handles/files until readers finish. A filesystem rename alone is not a cross-engine transaction, and open handles/rename semantics differ on Windows. Design activation, crash recovery and garbage collection explicitly. These are design obligations, not claimed engine features.

For incremental E, commit authoritative inputs first; make the projection consumer idempotent and checkpoint only applied input. A crash after SQLite commit must leave replayable work, not lost claims. Expose projection lag/failure; never combine current SQLite support metadata with an older engine's claim status as if one snapshot. For forgetting, retire affected generations/caches and prevent serving stale copies. These obligations follow the existing replay, scope and failure contract (`docs/adr/0009-claims-projection.md:25–33`; `docs/decisions/knowledge.md` §12, §14).

**Graph view over relational tables.** DuckPGQ declares vertex/edge tables and queries them with SQL/PGQ, with CSR acceleration for paths; this is a graph query/execution layer over relations, not necessarily a second authoritative graph. A copied DuckDB projection still needs E; querying external SQLite tables does not establish a shared cross-engine transaction. GraphQLite keeps the SQLite host and adds Cypher, but whether arbitrary existing claim/support tables can become its graph view without copying is **unverified**. [DuckPGQ example](https://duckdb.org/community_extensions/extensions/duckpgq), [paper](https://vldb.org/cidrdb/papers/2023/p66-wolde.pdf), [GraphQLite](https://github.com/colliery-io/graphqlite).

**In-memory inference beside durable SQLite.** differential-dataflow/DBSP suit repeated incremental joins and recursive derived relations; crepe/ascent suit fixed rules compiled with the application. They do not supply storage, open-ended graph query APIs, provenance semantics or crash recovery merely by computing a fixed point. Retractions need appropriate signed updates/recomputation and separate justification bookkeeping. [Differential](https://github.com/TimelyDataflow/differential-dataflow), [DBSP](https://github.com/feldera/feldera/blob/main/crates/dbsp/README.md), [crepe](https://github.com/ekzhang/crepe), [ascent](https://github.com/s-arash/ascent).

## Risks and options for the owner

- **Engine abandonment is concrete:** Kùzu stopped, Bighorn stopped, Cozo has no observed commit since 2024. Existing licences permit continued use under their terms; they do not provide vulnerability fixes, new platform builds or compatible future bindings. Active forks reduce immediate dependency risk but create their own maintainership risk. Sources: maintenance table and archive notices above.
- **The storage trait helps, but only partway.** ADR 0002's domain trait keeps engine-specific SQL/types out of callers (`docs/adr/0002-sqlite-fts5-storage.md:8`). It cannot conjure missing isolation, rewrite leaked query syntax or recover the only copy of an engine-specific value. Portable input export, versioned canonical encodings, replay, deterministic IDs, conformance fixtures and atomic activation are the actual exit path. A sidecar engine also needs a projection boundary, not just a replacement evidence-store implementation.
- **Library embedding and process concurrency are different questions.** Oxigraph's cross-process restriction and Ladybug/DuckDB's writer ownership mean that a single process service or immutable-generation copies may be needed. That changes Rastro's accepted reader architecture even though those engines are “embedded.” Sources: concurrency links above; ADR 0002 amendment.
- **Options, no selection:** SQLite offers the shortest route to present bounded reads; Oxigraph offers native RDF/SPARQL if semantic interoperability justifies mapping and process work; Ladybug offers maintained Cypher/analytical traversal with FFI/process constraints; GraphQLite/Grafeo/Helix offer newer local engines that need correctness/packaging evaluation; DuckPGQ offers relational graph analytics without making graph storage authoritative. Server baselines add mature query tooling but impose server ownership. No leaning recorded; owner decides after workload and model choices.

## Unverified

- Exact linked binary-size deltas for **every** engine; no release build was performed. Download/archive size, crate size, Docker image size and RSS are not substitutes. Grafeo's optional ONNX size claim is not the core-engine delta.
- Native Windows/build-matrix guarantees where marked `?`/`portable*`; exact Linux ARM64/macOS architecture support for each fork and extension version. Ladybug documents Rust builds tested with MSVC on Windows, GCC on Linux and Clang on macOS/Linux; equivalent guarantees for every fork are unverified.
- First-party evidence for Kùzu's reported acquisition/buyer and why Kineviz archived Bighorn. Fork count and continued code availability do not establish maintenance.
- Vela default-branch last commit and latest-release discrepancy: inspected feed names `2efa20b`, while repository-page release link exposed `87bf0be`; do not choose a revision from this note. Bighorn has no release entries in inspected feed, which does not prove no tags or external distributions.
- Repository “pushed_at” can reflect non-default branches. Dates explicitly labelled push above are not latest merged-code dates. GitHub “latest” can omit maintenance-stream publications; Neo4j's distribution date differs from tag/feed timestamps.
- Grafeo, Helix, SurrealKV, Cozo, IndraDB and GraphQLite: operation-level cross-process snapshot, crash and read-only guarantees required by Rastro. Same-process MVCC, an `open_reader` method or SQLite hosting alone is insufficient evidence.
- SurrealDB's 4.0 tag licence still labels Licensed Work “SurrealDB 3.0”; exact interpretation/change schedule and redistribution suitability not adjudicated. Server-engine enterprise feature/licence combinations require version-specific review; wrapper licences do not relicense bundled engines.
- Exact native text/vector support in Oxigraph/IndraDB; mark “not verified” rather than claim absence. SurrealDB 4.0 history/version retention, Helix historical reads, Grafeo bitemporal queries, and transactionally consistent AGE+pgvector integration were not established.
- GraphQLite arbitrary-table graph views, cross-connection index-cache invalidation, generation handling and rollback; DuckPGQ extension artifacts compatible with each required DuckDB/platform version. Do not fetch extensions dynamically in production without a packaging decision.
- No independent benchmark establishes that 10M Rastro claims satisfy an agreed latency/memory budget. No engine installs, crash tests, performance runs, repository code changes or git mutations performed for this note.
