## 1. Verdict

- **Strongest:** the temporal core and the scope rule. Occurrence-level intervals fix the O↔C cycle (`11` example); worked example (d) gets the hidden-replacement case right (`why(O)` personal `[09:02,10:10)`, A2 must not close B1; matches S28). - **Weakest:**

  2. **It front-loads about 60% of a platform** (RDF profile, nanopub packages, SHACL layer, artifacts, multi-binding) for an observed-only slice that needs about 12 of its 19 tables, and several of those pieces serve no consumer in the roadmap.

## 2. Findings (most severe first)

### F1. Retraction blocks the proposition forever; confirmation vs newer observation unspecified: **blocking** for adopting A9/Q4a
- **Claim:** `20` A9 "Retraction": explicit retract installs a scoped durable blocking rule against the target proposition until reversed; "explicit target block wins" over all alternatives. "A positive confirmation independently sustains the proposition". Q4a.
- **Wrong:** a proposition is `(subject, predicate, object)` with no time in it (D5; `20` rejects contextual IDs, Q6c). A block on it outlives the world state it was about. And a confirmation has no source clock, so the "newer comparable observation replaces" rule (knowledge §26) can't compare against it.
- **Failure scenarios:**
  1. *Retract, then the world makes it true.* Owner retracts `PR12 code:state closed` at 10:00 (a stale mirror said closed). PR12 really closes at 12:00; GitHub evidence says `closed` (structured, deterministic). The block still wins: `why(closed)` reads `retracted`, `about` omits it, an agent asking "is PR12 closed?" gets nothing, while the evidence is retained and cited. This breaks concept §1 (cited, correctable) and "success = owner stops checking sources". Replay can't fix it: the block is a precious input.
  2. *Confirm, then newer evidence.* Owner confirms `PR12 state open`. Source later reports `closed` (newer). The design never says which wins: the confirmation justification has no clock domain (`justification.clock_domain`/`source_updated_at` are provenance-only, `20:249-250`), so `open` stays `confirmed` and `closed` is `observed`; scalar → `conflicts_with` forever. Glossary "deterministic evidence = observed or confirmed" then lets an Act use the stale confirmed claim (levels §1).
  3. *Retract in personal, claim visible in work.* The block is "scoped" (§A9, Q2 note: default scope = Ask's context). A claim with evidence in both scopes stays `observed` under `--scope work`. Concept §1 says the owner can retract anything; knowledge §10 says retraction carries through to proposals and Action runs. A scoped agent launched on `work` can act on a claim the owner retracted.
  4. *Confirm after retract.* The owner ticks "yes" on a retracted claim. The block "wins", so nothing happens; only a separate `reverse_rule` event lifts it. Glossary "Confirmation = the owner's explicit yes" is silently ignored.
- **Evidence:** `20:136-137`, `20:249`, Q4; knowledge §26 (newer comparable observation), concept §1/§7, levels §1; `21` A9 asks the same Q4 but conditions less (confirmation anchored to the anchor claim; undo = cannot-link on a statement).
- **Fix:** bind a retract/reject to the *revision the owner saw* (its `seen_revision`, which the DDL already stores), so new structured evidence that changes the visible state re-raises an Ask instead of staying blocked. Define confirmed-vs-observed precedence explicitly (e.g. a newer comparable observation supersedes a confirmation of a scalar and raises an Ask; or confirmation expires on contradiction). Make retract global by default (owner chooses to narrow). Make a new yes on a retracted target an explicit `reverse` or an Ask, not a no-op. Treat Q4 as three questions, not one.

### F2. Read-time scope recompute: cost is O(degree), plans are fragile, and the reconstruction isn't specified at table level: **major**
- **Claim:** §1 "Scope-filter all justifications before computing identity, Status, revision, links or limits"; §A6/A10: scoped answers recompute rather than read caches; sort on computed visible known-time starts. Gate: p95 < 200 ms at 1M (§6).
- **Wrong / risky:**
  1. **Cost is proportional to the hub's degree before the limit** (the sort key is computed, so no index range scan can stop at `limit+1`). `21` keeps a per-lens `adjacency` table keyed by `known_since DESC`, so `about` is O(limit).
  2. **Plan fragility on the read path.** I built a 20k-claim hub (one justification, one span, one interval each, half work, half personal) in `20`'s DDL and ran the simplest possible visibility-filtered `about` (incident claims, visible justification via `support_span → evidence_ref.scope`, max interval start, `ORDER BY … LIMIT 20`). With no `sqlite_stat1`: **103 s** (SQL run; planner scanned and nested-looped badly). After `ANALYZE`: **35 ms**; with the join order forced: **22 ms**. So the design depends on the writer running `ANALYZE` at every generation activation (a read-only open cannot, ADR 0002 R14/R17). Nothing in §7 says so.
  3. **That 35 ms is a lower bound.** It uses stored full-view intervals as if they were scoped, which `20:345` itself says is wrong ("simply filtering globally closed intervals leaks hidden replacements"). The correct computation sweeps visible observations per field group. The DDL can't do that without joining the real `evidence` table: `evidence_ref` has only `(iri, local_evidence_id, scope, content_hash)`, and `justification` has no `field_key`/`location`/`captured_at` (`20:178-181,245-256`). The sweep input, its index and its per-call work are unspecified.
  4. **Inference visibility is recursive** ("AND derivation with any hidden premise is unavailable", `20:151`) with no depth bound stated, per call.
- **Fair credit:** this is the *simplest to keep correct*: no stored per-scope state to invalidate, any `--scope a --scope b` set works, nothing to garbage-collect. `21`'s lenses need registration, a copy of state per scope set and an incremental recompute that must equal replay (its own risk table).
- **Failure scenario:** MCP `about(bot)` under `--scope personal` on a bot with 50k comments across two scopes: every call scans 50k incident claims and sweeps their field groups before returning 20; with a cold plan, seconds to minutes.
- **Fix:** keep read-time as the *oracle* and add a derived per-scope-set cache (what `21` does), or add an `adjacency`-style index and the scoped sweep input to the DDL, and make `ANALYZE`/plan pinning part of generation activation. Benchmark the sweep, not the join.

### F4. Revision v2 includes vocabulary/rule hashes, so every claim's revision churns on a definition edit: **major**
- **Claim:** A10 "A scoped revision includes visible justification IDs, premise occurrence refs, policy/term hashes and links"; `justification.rule_version`/`vocabulary_hash` are NOT NULL (`20:248-249`); only "runtime run IDs" are excluded (`20:341`).
- **Wrong:** ADR 0009: "a revision change means the visible state changed"; renderers §5 targets claim id + revision. A typo fix to one `definition` field in `code`, or an extractor patch that reproduces identical supports, changes the term hash and so the revision of *every* claim of that predicate. Every renderer-held revision goes stale; every pending Confirmation (checked against `seen_revision`, `20:186`) is rejected as stale.
- **Failure:** owner has a confirm tick pending on `PR12 state`; the vocabulary plugin auto-updates `code` 0.1.0 → 0.1.1 (a counter-example added). Tick → "stale revision", although the state, supports and links are byte-identical. A→B→A vocabulary churn → repeated Asks.
- **Evidence:** `21` A8 "Revision keys exclude `extractor_version`, so an upgrade that reproduces identical supports leaves revisions unchanged"; `00` §6 inv. 6; `20` itself also says changed *meaning* needs a new IRI, so a hash of *definition text* in the revision is redundant with that.
- **Fix:** revision covers visible state only (status, visible support spans/evidence, links, validity), not the producing code's versions; versions live on the justification for `why`.

### F5. Occurrence/premise model has gaps: **major**
- **Claim:** A2/A3 "Replacements reference justifications/occurrences"; DDL `premise(justification, premise_claim, premise_occurrence)` with FK to `known_interval`.
- **Wrong:**
  1. **Premise names one occurrence of one justification of the premise claim** (SQL run: `premise_occurrence` FKs `known_interval`, which hangs off a single `justification`). If premise claim O has JA1 and JB1 (OR alternatives) and the premise points at JA1's occurrence, the inference dies when JA1 closes though O lives on via JB1. That contradicts the design's own "a Claim survives any alternative justification" and the J1=A∧B / J2=C test (§6).
  2. **Zero-length and adjacent intervals.** `known_interval` allows `end >= start` (`20:271`; SQL run: a zero-length row is accepted) while `valid_interval` requires `end > start` (`20:293`). A→B→A from one source in one capture batch is clamped to equal `captured_at` (`00` §1b, `SS/src/lib.rs:303-312`), giving C a zero-length `[t,t)` and O reopening at `t`. The design says "closed interval and later recurrence are different rows" (§A3) *and* "unioned Claim-presence intervals" (§3, A3): a union coalesces `[a,t) ∪ [t,∞)` into one presence and erases the recurrence the occurrence rows exist to keep. Which wins isn't specified. D15's "newest interval start" tie also then depends on claim ID.
  3. **Occurrence IRI minting is unspecified** (`known_interval.iri`, `justification.iri`, `claim_link.iri`): premises, links, confirmations and revisions all hash them, but the minting inputs aren't given, so "rebuild publishes identical … revision fingerprints" (§4a, §6) can't be checked.
- **Failure (2):** source A: `open@t`, `closed@t`, `open@t` (one batch, clamped). `why(C)` shows `[t,t)`; presence(O) shows one interval; `history` shows C superseded by O and O by C at the same instant. Two renderers disagree on whether O "recurred".
- **Fix:** premise references the premise *claim* (live ⇔ any live justification, per lens); forbid or explicitly normalise zero-length intervals (drop them, record a `transition` only); state the coalescing rule and the equal-timestamp order; put minting inputs in the spec. `21`'s `claim_interval` with `opened_by`/`closed_by` has the same shape and needs the same rule; it names the sweep but not zero-length either.

### F6. RDF 1.2 profile and nanopub-style packages: cost without a consumer: **major**
- **Claim:** A1/A2: "RDF 1.2 claim semantics", RDF 1.2 export, PROV-O, nanopub-style packages, RDF 1.1 fallback; Q8 leaning (a) "publish the profile now, build the serializer later".
- **Wrong / costly:**
  - Status (checked against `10` §Bottom line, which `20` also cites): RDF 1.2 Concepts is CR Snapshot, Semantics CR Draft, SPARQL 1.2, Turtle 1.2, SHACL 1.2 are WDs, JSON-LD has no triple terms, and the Interop note that defines the round trip is a *Group Note Draft* (2026-07-23). `20` §6 admits "Parser compatibility remains unverified", "no installed RDF parser/conformance run". So the profile is a spec for a serialization nobody can test yet.
  - It leaks into the schema anyway: `iri TEXT` primary/foreign keys in all 19 tables, `object_term` as a third object category, `urn:rastro:` namespaces, `rc:` terms. "No DB migration should be needed" if RDF 1.2 is dropped (§6) is untrue for the IRI keys and `object_term` that exist only for it.
  - **No consumer in the roadmap.** Export (sharing §1, roadmap slice 13) is "evidence, confirmations, rules and outcomes"; claims aren't exported. Sharing (slice 16) sends claims to *another Rastro* "as evidence from a person" (sharing §3); the receiver is not an RDF store. Nobody in `docs/` asks for SPARQL/SHACL/PROV tooling. The only stated purpose is "independently inspectable standard representation" (Q8c).
  - Two serializers (1.2 full and 1.1 statement node), a PROV mapping, a package mapping and golden fixtures must be kept in step with the model, forever, as drafts move.
- **Failure:** SPARQL 1.2 / Turtle 1.2 changes triple-term syntax after the profile is "pinned" in docs; the pinned profile and fixtures now describe a dead draft; Share work (slice 16) inherits a normative-looking spec.
- **Fix:** adopt `21`'s stance: statement-node JSON-LD 1.1 (works today, `10` §6) at the edge when sharing is built; keep `urn:rastro:` IRIs as the *only* standards-shaped commitment, if even that.

### F7. Injective prefix registry and preserving v1 hash inputs buy nothing stored and invite a collision: **major**
- **Claim:** A4: "Prefix expansion for existing predicate keys is a published, injective registry; retain their v1 hash inputs"; "Global naming enables matching".
- **Wrong:**
  1. **Nothing to protect.** The owner's DB has zero claims, entities or aliases (`00` §4, tables don't exist); main has no projection in prod; T4/T5 are unmerged. The only thing "v1 inputs" protects is the golden test (`crates/rastro-core/src/claims.rs:276-292`, `claim_id(pr, "code:state", open)`), and `21` A5 notes renaming type/alias claim IDs "is free now". Preserving v1 means two encodings live forever: a legacy path keyed by `code:state` and an IRI path for new terms, plus a forever adapter ("injective legacy-ID↔IRI", §5).
  2. **`urn:rastro:vocab:<prefix>:` has no naming authority.** Anyone's plugin may use `code`; the registry is "published" but nothing says who runs it or what happens on conflict. For Share (slice 16), owner B's `code:state` from a different `code` vocabulary has the same IRI and the same claim hash input: the exact semantic collision global IRIs exist to prevent. IRIs need an authority (a DNS-owned base, or the vocabulary package's hash in the IRI) to be "global".
  3. **Person IRI is inconsistent:** `urn:rastro:person:<hash(K,person)>` (§4b) vs "expose `urn:rastro:entity:e_…`" (A4); an Entity's ID is hash(canonical identifier) (claims.rs:`entity_id`), so the Person needs a canonical identifier (`21`: `person:intent/<id>`), otherwise Persons are the one Entity kind outside the ID scheme.
- **Fix:** before anything is stored, re-version once (new tags) with IRIs-or-not decided; if IRIs stay, put a namespace owner/authority rule into the registry and a version-agnostic vs version-specific policy for term IRIs.

### F8. Extraction artifacts as precious inputs: **major**
- **Claim:** A9/Q3a: artifacts become precious, exported, replayed; "Disable model/network … rebuild … on another machine: identical IDs, accepted submissions and scoped revisions" (§6).
- **Wrong / under-specified:**
  1. **Cross-machine replay is unreachable as specified.** Replay order and tie-break use local integer Evidence IDs ("equal timestamps ordered by Evidence ID", §A3/§3), revision v1 hashes `evidence_id.to_string()` (claims.rs, `revision`), and `evidence_ref.local_evidence_id` is the bridge. An import into another DB assigns new IDs, so scoped revisions and equal-timestamp order differ. Evidence needs a portable ID (content hash is already in `evidence_ref`) *in* the revision and tie-break.
  2. **Forgetting.** `artifact.request_context`, `raw_response` and `parsed_candidates` are TEXT copies of evidence content, outside `evidence`'s forget path and its marker. Knowledge §14/slice 14 require "forgetting carries through to everything derived". The design says artifacts are erased "as required" but gives no column-level or dependency mechanism; retired generations and exports hold more copies (§5 item 5 admits the purge).
  3. **Immutability not enforced.** `evidence` has insert-only triggers (`00` §1b); `20`'s DDL has none for `owner_event`, `confirmation`, `artifact`, `artifact_input` (SQL run: 0 triggers in the whole DDL). `21` adds them for `intent`.
  4. **Scope:** `artifact.scope` is one value, but artifacts hold inputs and outputs of the whole run; if a later extractor binding spans pairs (A8 lists), a single scope is wrong. "Artifact input visibility" is a prose invariant only.
  5. Amends knowledge §12 and sharing §1 (flagged, fair). `21` also adds an artifact table, so this isn't a differentiator, but `20` makes it mandatory for rebuild determinism while `21` keeps rebuild ≠ re-extract.
- **Fix:** portable evidence key; mark artifact content columns as "derived-from-evidence, scrubbable" with a forget path in the first migration that creates them; add triggers; or take Q3b (retain only confirmed interpretations) until slice 5 proves a need.

### F9. SHACL-style validator compiled from vocabularies: scope creep for little value: **minor**
- **Claim:** A5: "Core enforces a small SHACL-style profile", compiled from the installed vocabularies, SHACL 1.0-compatible export, differential fixtures (Q7a, §6).
- **Evaluation:** the genuinely valuable part is **bundle-atomic validation so type claims establish endpoint types regardless of message order** (replaces T5's "type claims first" ordering hack, `00` §3). But `20:341` then lists about fifteen invariants "FK/SHACL checks cannot replace" (spans, grants, acyclic premises, merge same-kind…): the core needs a bespoke Rust validator regardless. So the SHACL-like layer is a second mechanism covering a subset. "Differential fixtures against SHACL 1.0-compatible exported shapes" needs a SHACL engine in CI to compare against; none is identified (Q7b "complete third-party SHACL" is itself listed as heavier). `vocabulary_term` stores `domain_json`/`range_json` as JSON, so there is no relational vocabulary to compile from.
- **Failure:** the compiler and the export drift; the "restricted profile" accepts what a real SHACL engine would reject, and nobody notices because no engine runs.
- **Fix:** take `21` A5's fixed Rust checks plus conformance fixtures; keep the bundle-atomic type grounding as a design requirement (pragmatic's "anchor"); export shapes only when a consumer exists.

### F10. Merge components per scope; min-member display representative: **minor** (shared with `21`)
- **Claim:** A4: "scoped connected components; choose minimum visible member ID as display representative"; "grouped in the read result with all member Claim IDs and a group fingerprint".
- **Wrong:**
  1. Entity IDs are hashes, so the minimum is arbitrary, and it **changes when a new visible member joins** or when scope changes. Anything a renderer or agent keyed on the representative moves under it (`13` §3 already notes the "hash of sorted member set / min" row is unstable). `21` uses the same rule (`entity_state.cluster`, §3), so it doesn't discriminate between designs.
  2. **Grouping changes D15 by default.** Grouping is described as part of the normal read result; D15 (and S20–S23) define `about` as claims ordered by known time with `limit` 20/50. Does a group count as one toward `limit`? What is the group's Status and `revision` when members differ (one confirmed, one observed, a third added by a later merge)? Unspecified. `21` makes grouping opt-in (`expand: identity`) and leaves D15 untouched.
  3. Merge and Person minting compose: if two Persons are merged, `heldBy` links from accounts to both stay; `about(account)` follows to which Person?
- **Failure:** cluster `{e_5, e_9}` → merge adds `e_2`; the representative flips from `e_5` to `e_2`; a vault view that stored `e_5` as the "Ana" heading re-keys.
- **Fix:** no representative ID in the contract (return the member list, or pick the earliest-known member), make grouping opt-in, define group status/revision as a function of member claims.

### F11. Generation-keyed tables and "writer-collected after readers finish": **minor**
- **Claim:** A7: every projection row keyed by `generation`; "retired generations are writer-collected after readers finish".
- **Wrong:** the read path never writes (ADR 0002 R14/R17, `00` §6 inv. 9), so a reader can't register a lease, and a writer can't see other processes' reader transactions. Under SQLite WAL a reader holding one transaction keeps its snapshot even if the writer deletes the old generation, so waiting isn't needed; the real cost is that WAL checkpoints can't reclaim while it reads. Meanwhile the `generation` prefix is on every key and every query, which `21` A7 names as the cost it rejects, and it is only justified by shortening publication (flip a pointer vs. a copy-in of O(projection), `21` §1). `21` marks it as the fallback with a trigger (R10).
- **Fix:** state the collection rule (immediate, snapshot-safe) and the measured trigger for generation keys; start with T4's single-transaction swap.

### F12. Contradictions and amendments it didn't flag: **minor** (each small, one list)
- **Concept §1 "Correctable: the owner can confirm, fix or retract anything"** vs scope-bound retraction (F1.3). Not flagged.
- **Surfaces §23** says `about` accepts an entity id, canonical alias or exact URL and "anything else is an operation error naming the accepted forms". `20` A10: "bare names remain search candidates". Either an error or candidates; unflagged amendment.
- **Sharing §1 (Export)** is evidence, confirmations, rules and outcomes. `20` A2 puts "standard provenance packages" (claims, supports, revisions) in "portable export" (Q8). That's a Share artifact, not Export; Share is "evidence from a person" (sharing §3), which `20` does say, but then the package carries a revision/`rc:status` the receiver must ignore.
- **Glossary Intent** = `confirm, accept, edit, reject, answer, undo, stop, promote, missed`. `owner_event.kind` = `confirm, retract, undo_confirmation, block_merge, reverse_rule`: four unlisted terms (`retract` is a Status; AGENTS.md: use glossary terms exactly). `confirmation` is also a one-column table duplicating `owner_event(kind='confirm')`.
- **Knowledge §24** says an exact canonical identifier is one entity and "that is not a merge"; `20` A4 "source-vouched exact keys alone can automate identity" mixes the two meanings of "automate identity"; clarify which of entity-identity vs `merge` claim is automated.
- **A8 multiple bindings** amends plugins §15/ADR 0008 for a case that doesn't exist (one extractor today). `20` itself leans b (Q9), but the DDL already carries `binding`, `interpretation_slot` and `clock_domain` on every justification.
- **Not a violation, but note:** `valid_interval` writes one `unknown` row per occurrence for a time that is "unknown" until slice 5; absence would do.

## 4. Questions for the owner

1. **A9 semantics (F1): what does a retract block, and for how long?**
   (a) the proposition until a `reverse` (`20` Q4a); (b) the revision the owner saw, so new evidence that changes visible state re-raises an Ask (leaning of this review); (c) one occurrence only (`20` Q4c).
