# Knowledge of evidence

Status: agreed 2026-11-04. North star: `../concept.md` §1. Research: `../research/knowledge-graphs-2026-11.md`.

## Decisions
1. **Three layers.** Sources → **Evidence** (never changes) → **Knowledge** (claims about entities, derived and rebuildable).
2. **Evidence never changes.**
   - Each piece records its source, location (ID, URL or offset), capture time, the quoted span, and its trust class.
   - Forgetting (privacy) is the only removal, and it leaves a marker behind.
3. **Keeping raw content is the owner's choice per source:** the full original, or a pointer plus the span.
4. **One identity per entity, with many aliases.**
   - A merge is itself a claim, so it can be undone.
   - Matches on exact identifiers merge automatically. Fuzzy matches become an Ask. Names alone never merge.
5. **Claims.**
   - A claim is a statement about entities, with a status (`observed`, `hypothesis`, `confirmed`, `retracted`, `superseded`) and at least one justification (provenance, inference or confirmation).
   - When two sources say the same thing, that's one claim with two supports, not a duplicate.
6. **No span, no claim.** A claim drawn from unstructured content needs a quoted span from its evidence.
7. **Two times.** Valid time (when it's true in the world) and known time (when Rastro learned or unlearned it). "As of" queries are supported.
8. **Contradiction.** Conflicting claims both stay, and the conflict is visible. It gets resolved by newer evidence, by source authority, or by an Ask.
9. **Source authority.** Plugins declare defaults per kind of claim (for example "the tracker beats chat on task status"). The owner can override them.
10. **A retraction carries through** to:
    - derived claims;
    - pending proposals;
    - Action runs. An Action run whose basis was retracted is flagged, and an undo is proposed.
11. **Absence is knowledge.** Coverage records "found", "empty", "couldn't look" (with the reason) and "never looked" per source, scope and window. Past a source's freshness rule, the answer is "unknown", not "nothing".
12. **Knowledge can be rebuilt.** Knowledge = f(evidence, confirmations, rules). Swapping an extractor means replaying the evidence, not migrating data. Evidence, confirmations, rules and outcomes are the only precious inputs.
13. **Completion needs its own evidence.** A reply, or a related item reaching Done, doesn't prove a commitment was met.
14. **Scopes.** Evidence and claims carry scopes. Plugins and renderers see only the scopes they're granted. Forgetting carries through to everything derived from it.
15. **Retrieval.** Text search first, then expand 1–2 links through the graph. Summaries never replace the evidence.

## Added 2026-11-04 (roadmap slice 1)
16. **Raw content default:** pointer plus quoted span. Keeping the full original is opt-in per source, at registration. Replay covers only what was retained.
17. **A coverage window** is a half-open interval over the source's update time, plus a selection. A traversal cursor is how a connector resumes, not what coverage means. A window is complete only once every page and dependent read has finished.
18. **"Couldn't look" reasons** are typed: `auth`, `forbidden`, `not_found_or_hidden`, `rate_limited`, `network`, `timeout`, `protocol`, `interrupted`, `storage`, `result_cap` (the source caps how many results a query returns, so the read is incomplete; 2026-11-04), `not_installed` (the source's connector isn't installed; 2026-11-04), each with optional safe detail and a retry time. An incomplete read never becomes "empty".
19. **Re-observing unchanged content adds no evidence;** changed content appends. Encoding: `../adr/0005-evidence-observations-and-spans.md`.
20. **An empty search is not an empty source.** Search results always state the coverage of the sources they searched.

## Added 2026-11-04 (roadmap slice 2)
21. **Coverage is per (source, scope) pair, across config and storage.** The pairs are those in the config plus those only in storage (a removed source, or one whose scope changed). A pair that isn't in the config is `registered: false`. Its coverage comes from its stored windows: once the freshness rule has passed it reads "unknown", and a pair that never synced stays "never looked". So a hit always states its coverage (§20), even for a removed source. This decides the hit half of open question #9; the `source remove` command is still open.

## Accepted limits 2026-11-04
22. **Sources are keyed by name.** An old (source, scope) pair takes the source's current freshness rule, rather than a historical rule for that pair. While `rastro mcp` runs, its read-only reader uses fresh config without projection; the CLI projects config into storage. After a config edit, their answers for an old pair can differ until a writing open projects the change.

## Added 2026-11-04 (roadmap slice 3)
Architecture: `../adr/0008-extractor-role-and-protocol.md`, `../adr/0009-claims-projection.md`.
23. **Claims are observed only, from structured evidence.** An extractor's deterministic extraction rules, checked by the core, are the only source. Hypotheses wait for slice 5. No claim and no display name comes from a title or body.
24. **One exact canonical identifier is one entity,** across sources and scopes. That is not a merge (§4; merges are slice 4). No fuzzy or name matching, no bare-login lookup, no `about(me)`. Canonical identifiers: `github:account/<numeric id>` for accounts, with the login as an alias so a rename keeps the entity; the normalised `html_url`, fragments kept, for pull requests, issues, comments and repositories.
25. **Known time comes from evidence; valid time is `unknown`.** A known interval opens at the `captured_at` of the observation that establishes support and closes at the `captured_at` of the one that replaces it. An item-level update time is not when a field changed, so valid time isn't fabricated (§7). "As of" queries are slice 7.
26. **Supersession and conflict.** A claim is `observed` while any current support remains, and `superseded` once none does. `superseded_by` is set only for a scalar replacement. A missing or null field, an unreadable item or an item not returned never counts as removal. When sources disagree about the same resource and field, the newer comparable observation is current; a tie, or observations that can't be compared, leaves both `observed` with `conflicts_with` (§8). Conflict and supersession are computed from visible supports only (§14).
27. **Bots are kept.** Bot comments stay evidence and bots get author claims; filtering is for slice 5. The GitHub connector records the author as structured evidence at `/user/id`, `/user/login` and `/user/type` on items and comments. A null author records nothing: no author claim, no deleted-account guess. Kind, repository and comment parent come from the canonical `html_url` by a documented deterministic extraction rule, each tied to a structured observation of that location. List evidence stays per-index (`../specs/evidence.md` R38); list removal is unsupported (§31). Decides open questions #6 (for this slice) and #7.
28. **`rastro sync <source> --reread`** re-reads from the source's registered window start, under the normal append, unchanged and coverage rules. It can't recover past edits or items that left the selection, and an item not returned is never taken as deleted. CLI-only.
29. **Answers state extraction state** next to coverage: `not_installed`, `behind`, `running`, `failed` or `current`. An empty `about` is not "nothing known" (§11, §20).
    - *Precedence, 2026-11-05 (build):* `not_installed`, then `running`, then `failed`, then `behind`, then `current`. An unfinished run reads `running` only while a sync holds the lock; otherwise it reads `failed`. A pair whose only pending change is a new vocabulary version reads `behind`.

## Accepted limits 2026-11-04 (roadmap slice 3)
30. **Repository rename or transfer, and URL redirects,** give a new canonical identifier, so a new entity.
31. **List removal is unsupported.** List evidence stays per-index (`../specs/evidence.md` R38), so a removed element is not seen as removed.
32. **Rank leakage across scopes remains** as in `surfaces.md` §21; a scope isn't an isolation boundary until slice 14.
49. **A cold scoped read can miss its benchmark (accepted 2026-11-05).** On the gate's fixture (a 20k-item hub in a 100k-claim database), a scoped `about` took 372–415 ms p95 for one scope and 633–668 ms for two, cold, against a 200 ms target. Warm reads took 1.5–3.6 ms. Cost grows with hub size, and real hubs today are about 400 items. Exact recompute stays the only mechanism, with a per-scope-set cache and a work budget that fails honestly (`../adr/0009-claims-projection.md`). Revisit before roadmap slice 14 makes scopes an isolation boundary; persisted per-scope projections ("lenses") are the candidate.

## Added 2026-11-05 (knowledge graph deep dive)
Research and options: `../research/kg-deep-dive/` (`40-decision-brief.md`, `42-proposed-decisions.md`, owner log `41-owner-decisions.md`). Architecture: amendments of 2026-11-05 to `../adr/0008-extractor-role-and-protocol.md`, `../adr/0009-claims-projection.md` and `../adr/0002-sqlite-fts5-storage.md`. Observed-only stays the rule for the next slice (§23); the meaning of later slices is decided now so the schema stays open. Where an entry changes an older one, it names it.
33. **Claim ids are never re-keyed.** A claim id is a content hash. A merge, an unmerge or a retype never changes it.
34. **Amends §4: a merge is an overlay claim.**
    - It is undone without deleting history. There is no `owl:sameAs` and no OWL equality or functional-property reasoning.
    - An undo records a durable *cannot-link* that survives a rebuild, so a rebuild never re-creates the merge. One operation, no "undo versus they are different" choice.
    - A merge links entities of the same kind. An account is linked to a Person by a claim, never merged into it (`vocabulary.md` §14; glossary "Merge").
35. **Clarifies §5: one claim per exact statement; equivalents are grouped on read.** From slice 4, once a merge exists, `about` groups equivalent claims by default ("one identity per thing", concept §1).
    - A group carries all its member claim ids with their own statuses and revisions. Its revision is a hash of the sorted (member id, revision) pairs. It counts as one toward `limit`.
    - There is no representative id, and the group fingerprint is never a claim id.
    - A confirmation targets the member claims atomically. A change to any member shows as a conflict (`renderers.md` §5).
    - Slice 3 has no merges, so nothing changes there. The `about` result shape changes in slice 4 (additive). How a group of mixed statuses is shown is set in the slice 4 ADR.
36. **Person ids are never derived from email text.** Amends nothing in §24, and does not extend it.
    - A Person exists through an owner intent (an accepted Ask), an address-book resource id, or an owner Rule (a precious input, so automation is replayable and can be switched off).
    - Account-to-Person and email links are time-bounded claims. An equal vouched email *justifies* a reversible link to an existing Person, or proposes one as an Ask. Equal emails over non-overlapping intervals never join Persons. Two Persons are never joined by email alone.
    - No provider normalisation (dots in Gmail addresses) is baked into identity. The exact formula is set in the slice 4 ADR.
    - This honours §4: exact identifiers merge automatically, through the Rule path. Fewer automatic joins until a Rule or address book exists; meanwhile, Asks.
37. **History is stored per occurrence. Amends §25 and §26.**
    - An *occurrence* is one stretch during which one justification holds a claim. A claim's known interval is built from occurrences, not from accumulated claim-to-claim links. `superseded_by` marks only the current transition.
    - Transitions are ordered by event order: the observation's `captured_at`, then a portable key of the evidence, with the local evidence id only as the local tie-break. Equal timestamps are allowed; a closed occurrence and a later recurrence at the same `captured_at` stay separate. Intervals are half-open and may be zero-length.
    - *Corrected 2026-11-05 (confirmed by the owner):* within one `captured_at`, order is the order the evidence was stored, which an export keeps. The portable key serves identity only. See the 2026-11-05 correction in ADR 0009.
    - A claim is present when any of its justifications has an open occurrence, judged on event order, not timestamp.
    - Valid time stays `unknown` (§25). It is reported as `unknown`, with no stored column.
38. **Justification replaces claim support. Clarifies §5, §6 and §14.**
    - A justification (provenance, inference or confirmation) is one derivation. Several justifications on a claim are OR alternatives. Within one, the evidence spans and, once inference exists, the premise claims are all required (AND).
    - Forgetting any span of a derivation kills that derivation, and only that one (§14). "Two supports" in §5 means two derivations.
    - A premise is live while any justification of the premise claim is live. Cycles are rejected over the whole dependency graph (provenance, premises, confirmations); an anchor is not its own premise.
    - No blanket deletion of descendants: an independent proof survives.
39. **Amends §5 and §26 for several extractors on one field.** It stays one claim with several justifications, each labelled by its extractor. A count is not independent corroboration; `why` names extractors and sources separately. Authority across extractors is judged per field, not per rule. An owner override is a Rule, later.
40. **Retiring an extractor version.** A version bump replays the (source, scope) pair into new-version justifications. When that replay completes, the old version's justifications are replaced in one transaction with the final batch. Reads serve the old output until then, and a failed upgrade keeps the last good output. So a rebuild equals an incremental run, and the old and new interpretations are never both visible. One binding per source stays (`plugins.md` §15); a contract for several bound extractors waits until a second one exists.
41. **Inference.** A deterministic rule over observed or confirmed premises can produce an `observed` claim; inference over a hypothesis stays a hypothesis. A confirmation does not by itself grant an Act. Domain inference is not a core rule registry: no inference exists in the next slice. For slice 5, derivation is a replaceable plugin that submits claims with declared premises and the core validates them (`plugins.md` §18).
42. **Confirmation, retraction and undo (built in slice 7).**
    - A confirmation stores the full reviewed statement, insert-only and outside the rebuildable projection. It isn't re-checked at rebuild (§12).
    - An owner intent binds to the *lifecycle state the owner saw*: the claim's current occurrence plus its conflict and supersession links. Not the whole revision, so extra corroboration doesn't expire a yes.
    - A retraction hides the statement while that state holds. If the state changes (the occurrence closes, the claim is superseded, reopens after a gap, or gains a conflict), the retraction lapses: the claim reappears with its evidence-derived status, marked "earlier retracted", and an Ask is raised.
    - A confirmation keeps the statement alive on its own and survives a provenance change or an extractor's retirement. If the state changes it goes *stale*: shown with its history, no longer deterministic evidence, so no basis for an Act. An Ask is raised.
    - A new yes on a retracted claim is an explicit reverse; the latest owner intent wins, and it is recorded. Undoing a yes removes only the yes.
    - A permanent "never show me this again" is an owner Rule, not an intent.
    - An intent applies in every scope that can see a justification of its target. Its issuer must be able to see the target; an undo from a context that can't is refused.
    - Precedence: valid retraction, then valid confirmation, then deterministic observed (including a rule over observed or confirmed premises), then hypothesis, then superseded. This places confirmation in the order of §26.
    - A confirmation stores the exact reviewed claim set with its anchor identified. Rejecting the anchor retracts the slots whose only justification is conditioned on it. A slot with an independent observed justification survives, and the owner can retract slots one by one.
    - The exact definition of the lifecycle fingerprint, and how it differs from the revision a renderer sends, is set in the slice 7 ADR.
43. **Carry-through delivery (amends §10).** Until a durable outbox exists (written in the same transaction as the intent or the projection publication, with idempotent consumers, and proposals re-evaluated against alternative derivations instead of withdrawn wholesale), roadmap slice 8 may not run an Action on a knowledge-derived basis. Slices 6 and 7 emit events best effort; nothing executes on them.
44. **Scoped answers come from visible justifications only (§14, §26).** A hidden replacement never hides a visible claim, and no new global statistic feeds a scoped answer (the FTS rank leak stays the accepted limit, `surfaces.md` §21). The mechanism is exact recomputation at read time from visible justifications and visible intents. Stored full-scope state only accelerates unscoped reads. A benchmark gate on the real scoped read applies before the MCP-and-scopes ticket is signed off (`../plans/2026-11-04-claims-and-about.plan.md`); lenses are designed only if it fails, and a read that exceeds its work budget fails honestly instead of returning a weaker answer.
45. **Revision (clarifies `renderers.md` §5).** A claim's revision depends on its visible state only: status, the set of visible support keys (portable, deduplicated; no local ids, no versions), links and validity. A vocabulary definition edit or an extractor upgrade doesn't expire an owner's pending tick; `why` and the publication log tell "same state, new rules".
46. **Clarifies §12: what is precious.** In the next slice, evidence, confirmations, rules and outcomes remain the only precious inputs, and rebuild is replay through deterministic extractors. Direction for slice 5: a model's output is recorded, replayed, and never re-called at rebuild. Re-extraction is an explicit action that writes new records. Whether the recording is precious and exported, or only the owner's confirmed interpretations are kept, is decided when slice 5 is planned; expect the former. §12's text changes only then.
    - **Entry conditions for slice 5's migration:** insert-only triggers and a forget path for every copied payload in the migration that creates its table; a request's identity separate from an execution's; activating a re-extraction retires the older execution. Whether untrusted content may back a hypothesis only through an owner Rule is also decided then.
    - A vocabulary definition change means deterministic replay now. For hypotheses it will mean re-validate and mark `behind`, without a model call.
47. **"As of" and the served-answer audit (slice 7, §7, §25).** "As of t" is a reconstruction: recompute from evidence captured by t under today's pinned rules, and say so in the answer. One insert-only publication-log row per projection publication records the extractor and vocabulary versions and the evidence high-water mark. Answer receipts wait for a consumer. "Why did you say X on Tuesday?" gets today's rules on Tuesday's evidence; an Action run already records its own justification.
48. **Entry conditions for later slices.**
    - Slice 4: the identity ADR sets the formulas for Person minting and links (§36), group presentation (§35) and the core predicates of `vocabulary.md` §14.
    - Slice 5: §46, and §41's derivation direction.
    - Slice 7: the ADR defining the lifecycle fingerprint (§42).
    - Slice 7 (statuses `hypothesis` and `retracted`): the scoped replay forces `observed` on the claims it replays (`scoped.rs`), so scoped alias lookup would not exclude those statuses (`vocabulary.md` §20) and a scoped read could resolve through one. The slice that introduces them must replay the real status, or filter on it, before they exist in storage. Today the schema allows only `observed` and `superseded`.
    - Slice 8: §43.
    - Slice 16: `sharing.md` §8.
    - Slices 14 and 15 (scopes and forgetting; plugin install and permissions): does revoking a scope withdraw output already derived under it? (§51; `plugins.md` §5 lets the owner revoke a permission but doesn't say what happens to derived output.)

## Added 2026-11-05 (claims hardening)
Architecture: amendments of 2026-11-05 to `../adr/0009-claims-projection.md`. Plan: `../plans/2026-11-05-claims-hardening.plan.md`.
50. **`claims rebuild` carries over a pair that cannot replay (amends §40).** A (source, scope) pair whose bound extractor never started (not installed, failed its check, or its scope is forbidden, §51) keeps its last good output, as sync does. Carried over: its justifications, spans, claims, entities and checkpoint. Recomputed in full for every touched component: statuses, occurrences and links, so the lifecycle stays a function of evidence and justifications, and a claim shared with a rebuilt pair gets the same state as the incremental projection. An extractor that starts and then fails still aborts the whole rebuild and keeps the previous projection. The result lists every pair with its state and reason, and the CLI prints a line per carried-over pair, so the owner sees what was not re-derived (`surfaces.md` §33). The exit code follows sync's: non-zero when any pair reads `failed`; zero when none does (`not_installed` alone doesn't fail). On the owner's database a missing extractor would otherwise delete all 2248 claims.
51. **A forbidden pair is carried over and reads `failed`.** A pair whose scope is outside the extractor manifest's `permissions.scopes` is carried over like `not_installed` and reads `failed` with reason `forbidden`; there is no new extraction state (§29). The plugin sees nothing new, and scopes still filter reads (§14). The owner can revoke a permission (`plugins.md` §5), but whether revoking a scope withdraws output already derived under it is undecided; it is an entry condition for slices 14 and 15 (§48).
52. **Carried-over output is not precious (clarifies §12).** It is derived output kept only so a rebuild does not destroy the last good state. It is re-derived once the extractor returns, and carries no promise beyond that. Only evidence, confirmations, rules and outcomes stay precious. "Rebuild equals incremental" holds when every pair replays; carry-over has its own requirement in `../specs/claims.md` (applied at archive).

The result states whether it resolved (`surfaces.md` §39). Closes open question #10.
58. **Clarifies §34 and §26: an undone link or merge and an older name keep their history (2026-11-05).** They stay in the projection as `superseded`, with the interval closed at the undo (or the newer name's) time, so `about` and `why` still show them as history, and an older name still resolves as a historical alias (`vocabulary.md` §20). Architecture: `../adr/0010-identity-and-owner-intents.md`. Plan D36 (owner Q15): `../plans/2026-11-05-second-source-one-identity.plan.md`.

## Added 2026-11-06 (automatic links)
60. **Identity snapshots replace their predecessor.** A newer snapshot from the same source and selection closes claims supported only by the older snapshot, including a dropped address or an empty list. Only verified-email, token-owner and email-alias claims get this exception; other claims keep their lifecycle. Architecture: `../adr/0010-identity-and-owner-intents.md`. Plan D47.
61. **Automatic links are order-independent; owner links win.** A conflicting automatic link never displaces an owner link. Two cannot-linked accounts qualifying for one Person block each other only during their qualifying overlap, including through merged Persons; outside it each may join. Architecture: `../adr/0010-identity-and-owner-intents.md`. Plan D48 and D51.
62. **Hidden data may suppress an automatic link, never create one.** Owner refusals and automatic-link conflicts apply in every scope; only visible premises can create a link. An account may therefore stay unlinked without a visible reason. Architecture: `../adr/0010-identity-and-owner-intents.md`. Plan D50.

## Added 2026-11-06 (identity candidates and answers)
63. **Two explainable signals produce candidates, never automatic links.** `same name` compares full names of two words or more after lowercasing, removing Latin accents (precomposed or combining), and collapsing whitespace. A single first name does not count. `email matches login` compares an email's local part with the other account's login ASCII case-insensitively; a Linear email and a GitHub login are one such pair. At least one signal must match; both may be shown with their original values.
64. **Only unsettled accounts from different namespaces are candidates.** Bots (including `code:Bot` and `tracker:Bot`), Persons and untyped entities are excluded. Deactivated Linear users and Linear guests may be candidates. A pair is settled when one Person holds both accounts (merged Persons count as one), when the two accounts are cannot-linked, or when one account is cannot-linked to a Person holding the other, including through merged Persons. A pair within one namespace is never a candidate.
65. **The owner answers a pair that is a candidate now.** A no records a cannot-link between the two accounts, surviving a rebuild. A yes uses the existing Person holding either account and links the unheld account to it; merged Persons count as one holder. If neither account is held, a yes creates a Person and links both accounts. A yes over different, unmerged Persons is refused, telling the owner to merge or link by hand; it never merges them automatically. CLI and operation contract: `surfaces.md` §37. Intent mapping: `../adr/0010-identity-and-owner-intents.md`.
66. **A yes has a default name only when it creates a Person.** Use the longest name either account has, alphabetically first on a tie; if neither has a name, use the matched login. `--name <name>` overrides that default. It does not rename an existing holder.
67. **Undoing a yes can bring the pair back.** There is no permanent answered marker. Undoing one of the yes's links records its own cannot-link for that account and Person. The pair returns only if it still matches a signal and no settlement in §64 excludes it. Intent mapping and undo: `../adr/0010-identity-and-owner-intents.md`.
68. **GitHub profile emails are not read (2026-11-06, narrows plan D13).** A GitHub profile email is self-asserted and often empty; Rastro reads neither it nor any other unverified email from GitHub. Candidates rely on names and on verified Linear emails matching GitHub logins (§63). Architecture: `../adr/0010-identity-and-owner-intents.md`. Plan D61 (owner Q46).
