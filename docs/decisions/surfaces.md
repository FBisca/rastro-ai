# Surfaces: library, CLI, MCP

Status: agreed 2026-11-04. North star: `../concept.md` §5.

## Decisions
1. **The core is a library.** Every other surface is thin, the way the `hc` CLI and its API sit over herdr-core.
2. **The CLI and the MCP server are generated from one schema,** so they never drift apart.

| | CLI (`rastro`) | MCP |
|---|---|---|
| Best for | The owner, scripts, agents that have a shell | Agents, especially quarantined ones and hosts without a shell |
| Permissions | All or nothing (shell access is an outbound capability) | Per tool |
| Who is calling | Taken from the environment | Derived by the server, never declared by the caller |

3. **Reads** work over either surface.
4. **Writes from agents** (`submit`, `propose`, `ask`) go through MCP, because provenance and per-tool permission are the trust model. A quarantined extractor uses MCP only.
5. **Concept-level operations** the core offers agents:
   - `about(entity, since)`
   - `why(claim)`
   - `open_commitments(person)`
   - `coverage(source)`
   - `search(text)`, then follow 1–2 links
   - `propose(action)`, `ask(question)`, `submit(claim)`
6. **Platforms.** macOS and Linux are required; Windows is wanted.
7. **Future surfaces** (a native app, editor integrations, someone else's agent) drive the same library.
8. **Implementation language and process model:** see `../adr/0001-rust-core-out-of-process-plugins.md`.

## Added 2026-11-04 (roadmap slice 1)
9. **Every CLI command has `--json` output** from the versioned operation schema the MCP server will reuse. A failed `sync` exits non-zero.
10. **Data location:**
    - `RASTRO_HOME` overrides both directories (data in `$RASTRO_HOME/data`, config in `$RASTRO_HOME/config/config.toml`);
    - otherwise `XDG_DATA_HOME` and `XDG_CONFIG_HOME`;
    - otherwise `~/.local/share/rastro` and `~/.config/rastro`, on macOS and Linux alike.

## Added 2026-11-04 (roadmap slice 2)
Architecture: `../adr/0006-mcp-server-over-stdio.md` (the server, the pinned protocol revision, errors) and `../adr/0007-typed-operation-catalog.md` (one catalog for the CLI, MCP and the schema).
11. **MCP exposes `search` and `coverage` only.** `sync`, `source.*` and `index.rebuild` stay CLI-only. This is the first real use by agent tools, before claims or identity.
12. **A search hit shows why it matched.** It carries a `match` excerpt: centred on the first match, at most 400 bytes, cut at UTF-8 character boundaries, with offsets from the same origin as the span, plus `clipped_before` and `clipped_after`. Stemmed and diacritic-folded matches count, as in the index. If the match can't be located, the excerpt starts at the field's start with `located: false`. (Decides open question #8.)
13. **Bounded search.** Amends `../specs/evidence.md` R49, R60 (applied).
    - `quote` and `original` come back only with `full: true` (`--full` on the CLI). Human `--full` shows the whole quote, escaped and not clipped.
    - `limit` defaults to 20, range 1–50. `truncated: true` says more hits exist. Order is bm25, then id.
14. **Bounded coverage.** Each source returns its overall state, judged over all its windows, plus its 10 newest windows (newest first) and `windows_total`. `all_windows: true` (`--all-windows`) returns every window. Amends R63; R64 holds (applied).
15. **Scope is set by the owner at launch.** An optional, repeatable `rastro mcp --scope <s>` filters search and coverage inside the storage query, before the limit. A tool argument can't name a scope. No flag means all scopes. Per-plugin scope grants stay in slice 14.
16. **The caller is the owner.** The client's self-reported `clientInfo` grants nothing and isn't stored. MCP reads aren't plugin runs and aren't logged yet: plugins §9 logs plugin runs, and here the agent tool is a client, not a plugin Rastro runs. Logging reads is slice 9.
17. **Results are labelled, not enforced.** Hits keep their trust class, and the tool descriptions say results are data from sources, never instructions. Nothing is rewritten or fenced, and Rastro doesn't claim injection resistance: the agent tool still limits what the agent can do.
18. **Operation errors are results, protocol errors are protocol.** An error inside an operation is a tool result with `isError: true` and the v2 error envelope. An unknown tool, or arguments that fail the input schema, is a JSON-RPC error.

## Accepted limits 2026-11-04
19. **MCP tools declare no `outputSchema`.** The success schema would reject operation error envelopes; both remain v2 envelopes in `structuredContent` and text.
20. **Garbage stdin lines are silently ignored by rmcp.** They produce no stderr diagnostic.
21. **Launch scopes filter rows before the limit, but not rank statistics.** Full-text rank statistics span every scope, so hidden evidence can shift visible hit order. Accepted limit: a scope is not an isolation boundary until per-plugin scope grants in roadmap slice 14.

## Added 2026-11-04 (roadmap slice 3)
Architecture: `../adr/0009-claims-projection.md`, `../adr/0007-typed-operation-catalog.md` (one catalog entry per operation).
22. **Amends §11: MCP exposes `search`, `coverage`, `about` and `why`.** Both new operations are read-only, additive in the v2 catalog; existing contracts don't change. On the CLI: `rastro about <entity>` and `rastro why <claim-id>`. This amends `../specs/surfaces.md` R4, applied at archive. `sync` and `claims rebuild` stay CLI-only.
23. **`about(entity, since?, limit?, history?)`.** `entity` is an entity id, a canonical alias or an exact canonical URL; anything else is an operation error naming the accepted forms. It returns current claims where the entity is subject or object, one hop. `since` filters on known time; order is known time newest first, then claim id. `limit` defaults to 20, range 1–50, with `truncated`. `history: true` adds superseded claims. An unknown entity and one visible only through hidden scopes give the same empty result.
24. **`why(claim, limit?, full?)`.** Returns the claim (subject, predicate, object with display aliases, status, revision, known intervals, valid time, conflict and supersession links), the extractor, extraction rule and vocabulary versions, and its supports, bounded by `limit` (default 20, 1–50) with `truncated`. Each support carries evidence id, source, scope, location, field, span, `captured_at`, `source_updated_at`, trust class and a UTF-8-safe excerpt with clipping flags (§12); the full quote comes only with `full`. An unknown or hidden-only claim id is an operation error.
25. **Both state coverage** for every visible (source, scope) pair, plus extraction state per pair and extractor version (`knowledge.md` §29).
26. **Launch `--scope` filters every derived field** (resolution, aliases, types, status, revision, links, counts, extraction state) from visible supports before the limit (§15). A visible claim is never hidden by a hidden replacement.

## Added 2026-11-05 (claims hardening)
Architecture: amendments of 2026-11-05 to `../adr/0008-extractor-role-and-protocol.md` and `../adr/0009-claims-projection.md`. Plan: `../plans/2026-11-05-claims-hardening.plan.md`.
32. **Resolving through an old login (clarifies §23).** `about` then shows the subject's current aliases only; `why` on the alias claim shows its history. No contract change and no `resolved_by`; revisit with open question #10.
33. **Amends §22: additive results within v2.**
    - `sync`'s result carries an optional `extraction` object (run id, extractor, version, state, reason, evidence and claim counts), absent when no extractor is bound. It was added in slice 3 without a record here, contrary to the archived plan's D18 (`../plans/2026-11-04-claims-and-about.plan.md`), which kept existing contracts unchanged.
    - `claims.rebuild`'s result gains a `pairs` list (source, scope, run id, extractor, version, state, reason, counts), and the CLI prints a line per carried-over pair (`knowledge.md` §50).
    - Existing operations are unchanged except for additive changes recorded in this file.
34. **Entity forms are checked on syntax only (clarifies §23, §31).** No whitespace in the `e_` id, the URL, the namespace or the kind. Accepted: `e_` plus 32 lowercase hex; an exact URL with an RFC 3986 scheme and a non-empty rest (`<scheme>://<non-empty>`); `<namespace>:<kind>/<value>` with namespace and kind non-empty, kind without `/`, value non-empty (it may contain `/`, `[`, `]` and inner whitespace, never leading or trailing whitespace). `rastro:alias` is core, not GitHub: names from later sources contain spaces; the CLI quotes the form and MCP passes JSON. Anything else is an operation error naming the three forms (§18, §29). It is never a JSON-Schema `pattern`, so on MCP it is a result with `isError: true`, not a protocol error. A well-formed form that matches nothing gives the empty answer with coverage. Namespaces are not checked against plugins: the core cannot name `github` (AGENTS.md). Submit uses the same function (`../adr/0008-extractor-role-and-protocol.md`).
    - *Amended 2026-11-05:* the owner decided inner whitespace in the value on 2026-11-05; the first wording was no whitespace anywhere.
35. **Displayed type.** `about` and `why` show the most specific live type when an entity's types are compatible (`vocabulary.md` §15). When they conflict, they show the type with the newest known time, ties broken by claim id. One function; a scoped read computes it from visible justifications. No list of types and no contract change; the conflict stays visible on the type claims.
    - *Amended 2026-11-05:* live types (observed or confirmed) are grouped into compatible families, each headed by a most specific type (one no other live type descends from) and holding the live ancestors it carries. A family ranks by its newest member's known time, with ties going to the lowest claim id of the family's head; the newest family wins and its head type is displayed. Branching subtypes of one supertype are separate families that each count the supertype's time. Draft (day 1) under PullRequest (day 3) against Repository (day 2) displays Draft, because a recently seen supertype is the newest evidence for its family. The same function runs in a scoped read, over visible justifications only.
36. **Lookup does not check alias kinds against installed vocabularies.** Submit already checks kinds; a lookup check would break stored aliases after an extractor is removed.

## Added 2026-11-05 (roadmap slice 4)
Architecture: `../adr/0010-identity-and-owner-intents.md`. Plan: `../plans/2026-11-05-second-source-one-identity.plan.md`.
37. **`rastro identity` is the CLI for identity, and identity writes are CLI-only.** Writes: `rastro identity me`, `rastro identity person create --name <name>`, `rastro identity link|merge|undo`, and `rastro identity answer` (yes or no to a candidate). Reads: `rastro identity candidates` and `rastro identity history <entity>`. The MCP server stays read-only (§22): no MCP write operation for identity in this slice. This does not amend §4: agent writes still go through MCP when they come. `rastro identity me` is idempotent: a second run returns the same Person and records no new intent.
    - *Amended 2026-11-06:* `rastro identity candidates` and `rastro identity answer <account> <other> yes|no [--name <name>]` are CLI-only and read every scope, regardless of the launch scope filter. Neither is exposed on MCP. Answers name the two accounts, not a candidate id, and are refused unless that pair is a candidate now. Account arguments accept an entity id, canonical alias or exact canonical URL. Answer effects and naming: `knowledge.md` §65–67.
    - `rastro identity candidates --json` returns the v2 envelope below. Each pair has exactly two accounts, ordered by canonical identifier; pairs are ordered by those identifiers. `id` is the entity id, `identifier` its canonical identifier, and `held_by` lists the canonical identifiers of its current Persons. Each reason has a `reason` (`same name` or `email matches login`) and two original `values`, in account order. `name` is the default name for a Person a yes would create. An empty list is `candidates: []`.

      ```json
      {
        "schema_version": 2,
        "operation": "identity.candidates",
        "result": {
          "candidates": [{
            "accounts": [
              {"id": "e_11111111111111111111111111111111", "identifier": "github:login/ana", "held_by": []},
              {"id": "e_22222222222222222222222222222222", "identifier": "linear:user/u1", "held_by": []}
            ],
            "reasons": [{"reason": "same name", "values": ["Ana Silva", "Ana Sílva"]}],
            "name": "Ana Silva"
          }]
        }
      }
      ```

    - **Operation schema additions (v2, additive):** `identity.candidates` is read-only, takes `{}`, and returns `{candidates: [...]}` as above. `identity.answer` is a write with required string fields `account`, `other`, and `verdict` (`yes` or `no`), plus optional nullable string `name` (default absent). It returns `{intents: [...]}`, the accepted intents in acceptance order, through the existing identity-write result and v2 envelope. Both inputs reject unknown fields. Architecture: `../adr/0007-typed-operation-catalog.md` and `../adr/0010-identity-and-owner-intents.md`.
38. **`about` grows a Person view and `about me`.** `about me` resolves to the owner's Person. This amends §23 and §34: `me` is a fourth accepted entity form, reserved, and the error for anything else names the four forms. Any other bare word stays an operation error (§29). It lifts `knowledge.md` §24's "no `about(me)`". `about <person>` lists the Person, its linked accounts each with the reason it is linked (verified email, token owner, owner intent), and the claims of those accounts in one view, each claim citing its own account. Equivalent claims group (`knowledge.md` §35) and count once toward `limit`. `about <account>` shows the `rastro:held_by` Person. The existing work budget applies: exceeding it fails honestly instead of answering partially.
39. **The `about` result says whether it resolved.** An additive `resolved` field: `true` when the identifier resolved, `false` when it did not. A well-formed identifier that resolves to nothing visible (unknown, or hidden-only) gives `resolved: false` and the same answer as an unknown entity (§23, `knowledge.md` §57). MCP gets the same field.
40. **`source.add` takes source options (additive within v2).** The input gains `options` (array of `key=value` strings, default empty) and `repo` becomes optional (a shorthand for `--option repo=...`); `repo` leaves `required`. Nothing else in the operation changes. The options are validated against the connector's manifest (`plugins.md` §21).

41. **Coverage exposes partial-read gaps (2026-11-05).** `coverage` in CLI and MCP shows additive `gaps`, each with `{selection, reason}`, for selections the connector could not read. An otherwise successful run remains found/ok. Plan D45; `plugins.md` §26.
42. **`why` explains automatic links (2026-11-06).** On a `rastro:held_by` claim, each automatic justification has kind `inference`, reason `verified_email` or `token_owner` in `extraction_rule`, and evidence citations from its premise claims. The Person view's linked accounts carry the corresponding reason. Architecture: `../adr/0010-identity-and-owner-intents.md`.
43. **Email aliases display as `<namespace>:email/<address>` (2026-11-06).** `about` shows each email alias once in that canonical form, so the displayed address can be used directly for lookup (`vocabulary.md` §25).
44. **`sync` shows its progress on stderr (2026-11-12).** For each source, in order: a start line naming the source and why it reads what it reads (`first read from <window_start>` with no complete check, `incremental since <window_end>` otherwise, `re-read from <window_start>` with `--reread`); a `stage read`, `stage extract` and `stage project` line, where the extract line says `replaying <n> stored evidence` when the extractor reads evidence the read did not add (as after an extractor version change); a running item count, at most one per 2 s and only once a read has lasted that long, also while the connector is quiet (the count may then be 0); and a result line with `submitted`, `accepted` and `unchanged` counts, which for a `rate_limited` run adds `rate-limited, retry at <time>` from the stored outcome. The lines follow the connector's own relayed stderr in one queue, so what a connector prints after the start line shows after it. Stdout, `--json` and the exit code don't change: `sync --json` prints its one envelope, progress still goes to stderr. A stderr that is closed, broken or never read neither fails nor stalls a run: lines go through the host's bounded printer, which drops what it can't print, and the CLI's own error lines ignore a failing stderr. Plan D6; `evidence.md` R21, R23.
45. **`sync`'s result carries `warnings` (2026-11-12).** An array of strings, always present in a `sync` result (optional in the v2 schema, so earlier envelopes stay valid) and empty when there is nothing to warn of; additive, existing fields don't change. The first warning is the rename warning (`knowledge.md` §22): the same text goes to stderr, as `warning: <text>`, before the source's start line and its read. Plan D7.
46. **`about` and `why` give each claim's subject and object a `label` (additive within v2).** Every claim summary gains `subject_label` and `object_label`, next to `subject_aliases` and `object_aliases`: null, or `{text, url, evidence_id, field, captured_at, trust_class, clipped, state}`. `text` is the cited title or name, at most 200 characters (`knowledge.md` §69); `clipped` says it was cut. `url` is the entity's location when it is a URL, and null for a Linear issue. `state` is the value of the entity's current observed `code:state` or `tracker:state` claim, or null. A literal object has no label. The result schema lists both fields as required of a claim summary (they are always present), so a reader never has to tell a missing field from a null one. A `why` claim shows the labels `about` shows for it. A launch `--scope` takes labels and state from visible evidence and claims only (§26). The MCP descriptions of `about` and `why` say label text is untrusted data from a source (§17), the trust class travels with it, and the CLI text shows it after the entity's id (and aliases) as `"<text>"`, then `[<state>]`, with control characters escaped through the same display rule as other source text (§12). `--json` prints the same envelope MCP returns (§9). Architecture: `../adr/0007-typed-operation-catalog.md`.
47. **`about` filters by label state (2026-11-12, additive within v2).** The input gains `state`, an array of strings (default empty; CLI `--state`, repeatable). When it is not empty, `about` keeps only the claims whose subject or object has a label (§46) whose `state` equals one of them, compared without regard to ASCII case. The filter applies before grouping and `limit`, so `limit` and `truncated` count the matching claims only; for an entity that is not a Person, storage reads every claim of the entity rather than `limit + 1`. A claim with no labelled side never matches. It lets `about me --state open --state "In Progress"` answer "what is on my plate" without the closed history of a freshly read source filling the limit. Owner, switch day of plan `answers-i-can-read`.

## Added 2026-11-13 (meeting commitments)
48. **`meeting.import` and `meeting.commitments` (additive within v2).** `meeting.import` is CLI only and writes; `meeting.commitments` is read-only on the CLI and, as the MCP tool `meeting_commitments` (tool-calling APIs accept only letters, digits, `_` and `-`, so the dot becomes an underscore; the schema's operation entry says so in `mcp_tool`, which only an operation whose tool name differs carries), on MCP, and an MCP server limited to other scopes sees a meeting as unknown. Both return one result: the meeting, a notice that these are hypotheses, the latest run's extraction state (`succeeded` or `failed`, with `cause` and `reason`), coverage (`found`, `empty` or `couldn't look`, turns read and total), `results_from` when the listed hypotheses come from an earlier run, and the hypotheses. The CLI exits non-zero when the import's run failed. Product meaning: `meetings.md`; architecture: `../adr/0011-meeting-commitment-hypotheses.md`.
49. **`meeting.replay`, `meeting.forget` and `meeting.export`, and `stale` (additive within v2, 2026-11-13).** All three are CLI only. `meeting.replay` and `meeting.forget` write; `meeting.export` only reads. Replay returns the same result as `meeting.commitments`, with `extraction.replay_of` naming the run it checked again, and the CLI exits non-zero when the replay failed. A meeting that is unknown, or has nothing recorded, is an operation error, and nothing is recorded. `meeting.forget` returns what it removed. `meeting.export` returns the meeting, the owner's label, the explicit speaker mappings and the transcript only if it was kept. The result of `meeting.import`, `meeting.replay` and `meeting.commitments` gains `stale` (true when the hypotheses come from an earlier run than the latest, which failed) and `transcript_retained`, and `meeting.import` takes `--retain-transcript`. Product meaning: `meetings.md` §9–13.
50. **`meeting.import` calls the configured agent tool adapter (2026-11-13).** The operation, its arguments and its result are unchanged. What changes is who proposes: the adapter bound by `[commitment_adapter]` in `config.toml` (`plugins.md` §29–§33). A run whose adapter is missing, refused, unreachable, late or off-shape fails with the causes `extractor_unconfigured`, `extractor_failed` or `extractor_output_invalid`, which keep their names. The extraction's `extractor` field names the adapter's plugin id. Architecture: `../adr/0012-agent-tool-adapter.md`.

## Added 2026-11-13 (the commitments list)
51. **One `commitments` list over every source that has hypotheses (additive within v2).** `commitments` is read-only on the CLI (`rastro commitments [--source <name>] [--term <term>]`) and, as the MCP tool `commitments`, on MCP: the MCP tool set grows from five to six. It returns a notice that these are hypotheses and one entry per source (today a meeting) with the source's kind, name and scope, its latest extraction (state, cause, reason, run, adapter, replay, excluded), its coverage (`found` when the latest run looked, `couldn't look` with the reason when it failed), whether its results are stale, where they come from, and its hypotheses. Each hypothesis has the same shape whatever its source: status `hypothesis`, kind (`ask`, `promise` or `waiting_on`), promise, stated date or unknown, responsible and recipient (label, and the entity only when the owner mapped it explicitly, else null), exact quote with turn, speaker and byte range, and the standard terms it expresses. A source that found nothing, failed or couldn't be looked at is listed, never left out; a source filter that matches nothing, or a term nothing expresses, gives an empty list, not an error; a term filter keeps a source whose last run failed, because its gap is the answer. A launch `--scope` hides the sources of other scopes, and the read still succeeds. The list never says a commitment is open, done or tracked. `meeting.commitments` and the MCP tool `meeting_commitments` stay: removing an operation is not additive, so they go with the next schema version. The concept-level `open_commitments(person)` is reconciled to this list, because a hypothesis cannot assert "open". Spec: `../specs/commitments.md`.


## Added 2026-11-17 (the commitments queue)
52. **One `queue` read joins the commitments list's hypotheses and identity's candidates (additive within v2).** `queue` is read-only on the CLI (`rastro queue`, no arguments) and, as the MCP tool `queue`, on MCP: the MCP tool set grows from six to seven. Its result is a v2 envelope holding `notice`, one flat `items` list and one `gaps` list.
    - Each item has a `kind` (`proposal` or `question`), a `source` (`kind`, `name`, `scope`), and a content-addressed `id`: `q_` plus the first 16 bytes of the SHA-256 of its canonical encoding (the encoding a claim's id uses, under the queue's own domain). A proposal's content is its source and hypothesis, so a re-import or replay of the same content keeps its id; an item whose content changed is a different item. A question has no time, so it sorts before every proposal and its order is its accounts' identifiers; proposals are oldest first by the meeting's capture time, then by turn.
    - A **proposal** carries the `commitments` list's hypothesis shape in `proposal`: status `hypothesis`, kind (`ask`, `promise` or `waiting_on`), promise, stated date or unknown, responsible and recipient (label, and the entity only when the owner mapped it explicitly), exact quote with turn, speaker and byte range, and the standard terms it expresses. A **question** carries in `question` its two accounts (entity id, canonical identifier, and the current names it goes by, sorted), the signals that produced the pair with their original values, and the name a yes would give a new Person. A question names the identity graph as its source: kind `identity`, name `identity`, empty scope. Same-person candidates are computed over every scope, so only an unscoped caller is shown a question; a caller with launch scopes is shown none.
    - Each source that found nothing, failed or couldn't look names its **gap**: `{source, state, run, cause?, reason?}`. `state` is `found_nothing` (the latest run looked and proposed nothing), `failed` (the latest run failed, with its `cause`) or `could_not_look` (the content could not be read, with its `reason`). A source whose later run failed keeps the last good run's proposals and names the gap beside them, never silently dropping them. A source in a scope the caller can't see is absent with its gap, and the read still succeeds.
    - The list never says a commitment is open, done or tracked. Item ids are what the later queue writes name.

## Added 2026-11-17 (the queue's answers)
53. **The queue's five answers are CLI-only writes, one owner intent each (additive within v2).** They are the catalog operations `queue.accept` (`rastro queue accept <item>`), `queue.edit` (`rastro queue edit <item> [--promise <text>] [--date <text>]`), `queue.reject` (`rastro queue reject <item> --reason <text>`), `queue.answer` (`rastro queue answer <item> yes|no [--name <name>]`) and `queue.missed` (`rastro queue missed <text> [--item <item>]`). All five are CLI only, as §37 made identity's writes: nothing on the owner's behalf answers a queue, so the MCP tool set stays at seven (§52), an MCP client that calls `queue_accept` or any of the other four gets a JSON-RPC error (`-32602`, unknown tool), and nothing runs or is recorded. Each returns `{item?, intents: [...]}` — the item it named, absent for a missed report about nothing queued, and the owner intents it accepted in acceptance order — through a v2 envelope. The published schema gains the five operation entries and their envelope branches; every earlier operation's schema is unchanged.
    - **One intent per answer.** An `accept` intent carries the proposal it accepted and the statement the owner saw; an `edit` intent carries the statement seen and the one the owner made (an edit that changes neither the promise nor the stated date is refused, and `accept` is what accepts unchanged); a `reject` intent carries the owner's reason; a `missed` intent carries the owner's words and, when one was named, the item; an `answer` intent carries the question item, its two accounts, the verdict, and for a yes the Person that holds them and, when the answer creates it, its name. One answer is one row whatever it decides: a yes to a pair no Person holds yet records one `answer` intent, never a creation plus a name plus links, and the claims it decides — the Person's type, its name, each held-by claim — are justified by that intent alone. `identity.answer` keeps its own shape. A rejection mints no claim.
    - **An item gone is refused.** An answer naming an item the queue no longer holds — never queued, already answered, or replaced by a re-import, which is a different content-addressed item — is an operation error naming the item, and nothing is recorded: no intent, no claim, and the queue reads the same before and after. Answering the same item a second time is that same refusal.
    - **What leaves the queue.** An accepted, edited or rejected proposal leaves the queue on every surface, because the read leaves out any proposal an answer names; a question leaves because its pair is no longer a candidate (a no is a cannot-link, a yes holds the accounts); a missed report leaves its item waiting, because it reports something about the item, not an answer to it. The CLI text of an answer names the item and prints each accepted intent with its issuer, domain and status.
    - **What an answer decided is recorded, not recomputed.** A question's answer carries, in its own row, the accounts it links and the Person it creates when it creates one. A replay reads those and nothing else, so a later intent on one of those accounts — a link undone, say — never changes what an earlier answer said, and undoing the answer ends the held-by claims and the name (they stay as ended, not erased, as an undone link's do) while the question waits again. A no can't be undone, as a cannot-link can't; a yes that created a Person can't be undone once a later intent holds, names or merges that Person (the refusal names that intent), because its undo would leave a held-by or name claim pointing at something that is no longer a Person.

## Added 2026-11-19 (roadmap slice 8a)
54. **Actions: one read on both surfaces, the writes on the CLI (additive within v2).** `actions` (the runs, or one run with its proposal, why, cited claims and evidence, accept intent, level and cell) is a catalog read on the CLI and MCP, visible only in scopes that see the source the run writes to. `actions propose` and `actions undo` are CLI-only writes; an agent in any harness proposes through the shell (§37).

## Added 2026-11-19 (roadmap slice 8b)
55. **Rules: the check on both surfaces, the stop on the CLI (additive within v2).** `rules check` (each rule's match, grace, cap, today's count, pending Acts and the queued proposals it matches) is a catalog read on the CLI and MCP, and records nothing. `actions` shows a pending Act with the time it runs and its stop command. `actions stop` is a CLI-only write, and nothing on MCP writes a rule.
