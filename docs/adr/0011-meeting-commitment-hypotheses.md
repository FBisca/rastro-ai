# Meeting commitment hypotheses: a one-shot extractor command, kept outside the claims projection

A user imports one speaker-labelled transcript for one meeting. A configured extractor proposes commitments that involve the owner; the core checks each proposal against the transcript and keeps the survivors as **commitment hypotheses**, each with its exact quote. Product meaning: `../decisions/meetings.md`.

## Shape
1. **Operations (catalog, ADR 0007).** `meeting.import` (CLI only, writes) and `meeting.commitments` (CLI and MCP, read-only, on the CLI's read path; the MCP tool is `meeting_commitments`, because tool-calling APIs reject dots in tool names). `meeting.import` returns the same result a later `meeting.commitments` read returns, and the CLI exits non-zero when its run failed. A run that fails is a result, not an error: it is recorded with its cause (`source_unreadable`, `transcript_invalid`, `owner_unmapped`, `owner_not_in_transcript`, `mapping_invalid`, `extractor_unconfigured`, `extractor_failed`, `extractor_output_invalid`, `invalid_quote`, `storage_failed`). Only a request that cannot name a meeting (empty identifier or scope, a speaker mapped twice, a bad `--speaker` form) is an error and records nothing.
2. **Transcript format.** Plain text, one turn per `Label: text` line (the colon followed by white space or the end of the line). Any other non-blank line continues the turn before it. At most 4 MiB of UTF-8.
3. **Extractor adapter (superseded 2026-11-13 by ADR 0012: an agent tool adapter plugin bound by `[commitment_adapter]`; the shape below is what it replaced).** `config.toml` holds `[meeting_extractor]` with `command`, optional `args` and `timeout_seconds` (default 120). The core runs it once per import, writes one JSON request on stdin and reads one JSON response from stdout (at most 4 MiB). Its stderr is drained to the end, so a chatty extractor is never killed by a closed pipe; only the first 2048 bytes are kept as the reason when it fails. The request has the protocol name, the core's `instructions`, the meeting, the owner's speaker label and the `turns`; the transcript text appears only in `turns[].text`. The response is `{"candidates": [{turn, responsible, recipient, promise, stated_date, quote}]}`, unknown fields denied. The configured command is the owner's authorization to send transcripts to it; it is not a plugin and holds no grants (ADR 0004), so it is not offered to anything but this operation.
4. **What the core checks, itself.**
   - The quote is a non-empty, exact, contiguous piece of the named turn's text. Any candidate that fails (even one the owner is not in) fails the whole run.
   - The transcript, not the extractor's labels, has to support the owner's side. The candidate must name the owner as responsible or as recipient, and then: **owner responsible** needs the quote in the owner's own turn, or naming the owner's label; **owner recipient** needs the quote in the owner's turn, or naming the owner's label, or addressing the listener in the second person (`you`, `your`, `you'll`, ...) in a turn adjacent to an owner turn. Naming is a whole-word, case-insensitive match of the label. Otherwise the candidate is left out and counted (`excluded`), and nothing of it is stored: a promise between other people stays out even when the extractor puts the owner on it.
   - A stated date is kept only if it is a piece of the quote; otherwise it reads unknown.
   - People: the owner is the Person `me`; other labels resolve only through explicit `--speaker label=entity` mappings to existing entities. A label that is not mapped, or that the extractor names without it being a speaker, stays `unknown` and is shown by its label. Names never resolve to identities.
   - Candidates are never merged or reordered; repeats stay separate hypotheses.
5. **Storage.** Migration `202611131000_meeting_commitments`: `meeting` (identifier, scope, capture time), `meeting_run` (state, cause, extractor, turns read and total, excluded count) and `meeting_hypothesis` (per run: both people as the label and the resolved entity, promise, stated date, turn, speaker, quote and its byte span in the turn). A successful run replaces the hypotheses of earlier runs in the same transaction; a failed run adds only its run row. A read shows the latest run's state and the hypotheses of the latest successful run, saying so (`results_from`) when they differ. The transcript is not stored.
6. **Scope.** A meeting belongs to the scope given at import. A reader limited to other scopes (`rastro mcp --scope`) gets the same error for it as for an unknown meeting. Importing an existing identifier in another scope is refused before the transcript is read or the extractor runs, so a refused import never sends the transcript out.

## Considered options
- **Route hypotheses through the claims projection (ADR 0009).** Rejected: the projection takes deterministic extractors over structured, insert-only evidence (ADR 0008), while this input is untrusted, the output is not reproducible, and the supporting text has to be forgettable. A later slice can promote an accepted hypothesis into a claim with its own acceptance rule (ADR 0008's note on slice 5).
- **A manifest-declared extractor plugin.** Heavier than the need and grants nothing useful here; the configured command is explicit and narrow. Revisit with the agent tool adapter.
- **Core-side name matching to find people.** Rejected: it would infer identity from names (`../decisions/knowledge.md` §54).

## Consequences
- Recorded output, replay without a model call, stale results, retention and forgetting build on `meeting_run` and `meeting_hypothesis`; see Amendment 2026-11-13 below.
- The owner's mapping is per import, not remembered.

## Amendment 2026-11-13: replay, retention and forgetting
Migration `202611131100_meeting_retention` adds `meeting_run.replay_of` and four tables.
- **Recorded output.** A successful run writes `meeting_output` (the candidates the core kept, as the extractor proposed them, as JSON), `meeting_span` (the turns those candidates cite, with their text, and the turns beside them, speaker only) and `meeting_speaker` (the mappings used, the owner's included). Candidates the core excluded are not recorded, matching §4. Only the latest good run keeps them: a later success deletes the earlier runs' copies in the same transaction, and a failed run writes none, so the last good record stays replayable.
- **Replay** (`meeting.replay`, CLI only) reads that record without a transcript or an extractor, runs the same checks (§4) over the spans, and records a run with `replay_of` set to the run it checked. It writes the record again for itself. A check that no longer passes is a failed run with its cause, so the earlier results turn stale as in §5. The count of excluded candidates adds those of the replayed run. With no recorded output it is an operation error and records nothing.
- **Stale.** A read reports `stale` when the hypotheses are older than the latest import: the latest run failed and they come from an earlier good run, or the latest run is a replay of a record that predates a later import (a failed re-import, then a replay). A replay is no fresher than the import its record traces back to (following `replay_of`), so it never clears staleness; only a successful import does. `results_from` names the run the results come from (§5).
- **Transcript retention.** `meeting_transcript` holds the full text only when the import had `--retain-transcript`. Any import that reads a transcript replaces what was kept: with the opt-in, the new text; without it, nothing. A run that never read it (unreadable file) leaves it as it was.
- **Export** (`meeting.export`, CLI only, read-only) writes the meeting identity, the owner label, the explicit mappings of the latest good run and the retained transcript if any. Hypotheses, recorded output and spans are not exported (the slice-13 export of precious inputs, `../decisions/sharing.md` §8, will take this as it is).
- **Forgetting** (`meeting.forget`, CLI only) deletes every row kept for the meeting in one transaction, then truncates the write-ahead log. The connection sets `secure_delete`, so deleted pages are overwritten and a replaced result does not linger in a free page of the database file. A copy in a backup, or in a write-ahead log a concurrent reader holds, is outside what the core can scrub.
- **Rejected: keeping the whole extractor response for replay.** It would store the candidates the core excluded, about people the transcript does not tie to the owner. Rejected: replay re-checks only what was kept.
- **Rejected: replay as an unrecorded read.** A replay that fails its checks has to turn the earlier results stale, and a replay that succeeds has to show which run it came from, so each is a run.

## Amendment 2026-11-13: the extractor is an agent tool adapter
`../adr/0012-agent-tool-adapter.md` replaces §3: the configured one-shot command becomes a plugin of kind `agent-tool-adapter`, bound by `[commitment_adapter]`, spoken to with `judgment.request`, whose response the core validates strictly. §4's checks, §5, §6 and the replay amendment are unchanged. A candidate carries the adapter's `kind` (`ask`, `promise` or `waiting_on`), kept in `meeting_output.candidates`; output recorded before it replays without one. The "manifest-declared extractor plugin" option above is now the decision. Status stays accepted.
