# Judgment sessions: capped retry turns under core-executed gates

Owner direction 2026-11-20 (`../decisions/plugins.md` §38–43): tasks and actions declare their own validation gates and retry turns, always capped. Example: an agent returns an invalid id; the same session gets a second turn carrying the failure reason. This ADR shapes the protocol change; it is end-goal, not first delivery — the shipped one-shot `judge_text` path (ADR-0012) is untouched until an implementing slice.

## Decision
1. **One session per run, N turns max.** A task run opens one adapter session. The core sends the task's instructions (from its template plugin, §40), input and output schema; the adapter answers; the core executes the task's declared gates. A gate failure sends the failure reason back as the next turn of the SAME session; a pass closes it. The turn cap is declared per task, with a core maximum; time and cost caps bound the session regardless of turns.
2. **Gates are declarative, core-executed.** A task template declares its gates (shape, exact-quote/span rules, id resolution, field bounds) and which are retryable vs fatal. The core runs them; the adapter never validates its own trust boundary. A fatal gate, an exhausted cap, a timeout or a malformed answer fails the run; last good results stay, marked stale (ADR-0011 §5 unchanged).
3. **Every turn is recorded.** Requests, answers and gate verdicts of all turns — including failed ones — are recorded as the run's history; only the final validated output becomes evidence (recorded output, glossary). Replay re-checks the retained output with no model call, as today. Recording granularity and export/forget treatment of failed turns: open question 16.
4. **Harness continuation through thin drivers, with a degraded mode (amended 2026-11-20, owner-approved A+B).** Each adapter drives its harness CLI directly over the shared SDK; agent-runtime is an optional adapter, never a dependency (§36 amended). Verified locally 2026-11-20: pi `-p --session-id <id>` creates/uses a chosen session and `--session-dir <dir>` relocates storage; codex `exec resume <id>` resumes and `--output-schema <file>` constrains the final answer; claude `-p --resume <id>` continues a session. The shipped claude adapter sets `--no-session-persistence` — session-capable runs must drop it. Session ids: pi's may be the run key (deterministic); claude/codex ids are parsed from the first turn's structured output and persisted in the run record. A harness without usable resume degrades to a fresh turn carrying the prior answer and the failure reason as context; the degradation is recorded, never silent. Resume reloads saved state into a NEW process each turn — no live process persists; history consumes context under each harness's compaction, which the turn cap bounds. ADR-0012 §3's "no long-lived adapter process" is amended to: no process outlives its run; a session lives exactly as long as its capped run.
5. **Same shape for both adapter classes.** Agent-adapters and decision-adapters (System-1) speak the same session protocol; a decision task is typically a 1-turn session with a cheap gate set. Caps and cost class differ, the contract does not.
6. **Lockdown is declared by the task/action, enforced by the adapter, matched by the core (owner refinement 2026-11-20).** The task template (or action declaration) carries a boundary profile: tools off/allowlist, MCP servers permitted, sandbox mode, setting sources, session persistence. The adapter translates that profile into its harness's controls and declares in its manifest which boundary controls it can enforce (extends §29's capability model). Before a run, the core matches the task's required profile against the adapter's declared enforcement; a mismatch refuses the run naming the unenforceable control — never a degraded-security mode. The core floor is non-negotiable and not task-declarable: the reader/writer firewall (§6, §30) and "untrusted text is data, never instructions." Per-harness flag kits (claude `--tools ""` etc., codex read-only sandbox) are the adapter's translation table, re-applied on EVERY turn — launch flags do not persist across resume. pi's tools-off enforcement is UNVERIFIED (no flag in `pi --help`): a pi adapter declares that capability only after a contract test proves it; tasks requiring tools-off refuse pi until then. Judgment never grants workspace-write or test-execution tools: the task is text-in/structured-out, not coding.
7. **Session state lives under RASTRO_HOME where the harness allows.** pi: `--session-dir` under the run's home. claude/codex: their config-dir environment variables (names to be confirmed by contract test), else the residual session store in the owner's home is disclosed and slice 14 forgetting covers only what Rastro controls. Session files contain untrusted transcript text; they are part of the retention/forgetting surface (open question 16).
8. **Two failure classes, handled differently (owner refinement 2026-11-20).** A GATE failure — well-formed answer, failed validation — earns a retry turn: core-authored structured feedback (gate id, field, expected, actual; deterministic core text, never model prose, never transcript content re-framed as instructions), same session, capped. A SYSTEM failure — nonzero exit, crash, timeout, malformed wire, unavailable resume — is an error, classified recoverable or not: recoverable (transient timeout, crash with a saved session) is retried/resumed by tick within the run's caps (slice 8a recovery precedent); non-recoverable (adapter cannot start, manifest refused, unenforceable lockdown, caps exhausted) fails the run, last good results stay marked stale. Exit codes are system signals, never validation verdicts: the adapter parses the structured result (claude's result object incl. error flag, codex JSONL turn events, pi json/rpc events) for gate verdicts, and treats process failure as error regardless of any partial output. Recovery is idempotent and recorded; no partial writes escape a failed turn. Owner-approved defaults (2026-11-20, decides open question 15; `../decisions/plugins.md` §45): turn cap 3, per-turn timeout 120s, session cost cap owner-set; gate failures retryable, fatal and recoverable sets as above; configurable per task under core maxima.

## Considered options
- **Mandating agent-runtime for every agent call (former §36).** Rejected by the owner 2026-11-20: it pulls `hc` and agent-runtime into every adoption, against concept §5 (library first). It survives as one optional adapter implementation; thin CLI drivers over a shared SDK are the default.
- **One-shot, fail and re-run fresh (today).** Rejected as the only mode: loses the model's context, pays full input cost again, and cannot express "fix this specific field" — the owner's retry-turn example. Kept as the 1-turn case and the degraded mode.
- **Unbounded retries until valid.** Rejected: runaway cost and latency; a determined invalid answer loops forever. Caps are the point.
- **Adapter-side validation with retry inside the adapter.** Rejected: moves the trust boundary into the plugin that reads untrusted text (§6, §30); the core must own every gate.
- **Core-side retry with a new session per turn.** Rejected as default: same cost problem as one-shot re-run; kept only as the one-shot harness fallback, recorded.
