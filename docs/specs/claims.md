## Requirements
- **R1** WHEN a sync accepts evidence for a source bound to an extractor, THEN the extractor runs over that (source, scope)'s pending evidence, its claims can be read through `about` and `why`, and the extractor run is logged as its own run with plugin id, version and counts; the source's coverage is the same as without the extractor. (from claims-and-about/S3)
- **R2** WHEN an extractor submits a claim whose support is untrusted evidence, evidence not delivered to that run, a span outside its evidence, or a rule not declared deterministic, THEN the core records nothing for that claim and counts it rejected. (from claims-and-about/S4)
- **R3** WHEN a submitted claim's predicate isn't in the vocabulary, or its subject or object breaks the predicate's domain or range, THEN it's rejected and counted. (from claims-and-about/S4a)
- **R4** WHEN one span of a claim's support bundle fails a check, THEN the whole claim is rejected and counted, even though its other spans pass. (from claims-and-about/S4b)
- **R5** WHEN a submitted claim has an endpoint whose type isn't given by a `rastro:type` claim in the same submission, THEN it's rejected and counted, even if an earlier submission typed that entity; WHEN a submission's `rastro:type` disagrees with a type live anywhere on the entity (any location, any submission) and neither is a `supertype` of the other, THEN both stay visible as a conflict (R48). (from claims-and-about/S4c)
- **R6** WHEN a source's bound extractor isn't installed, THEN the sync succeeds and `about` reports extraction state `not_installed` for that pair; WHEN an extractor is installed but not bound to the source, THEN it never runs; `claims rebuild` carries that pair's output over instead of dropping it (R42). (from claims-and-about/S5)
- **R7** WHEN an existing GitHub source is loaded, THEN it is bound to `rastro-extractor-github` without the owner editing config. (from claims-and-about/S6)
- **R8** WHEN two sources observe the same PR with the same state, THEN there is one PR entity and one `code:state` claim with two supports. (from claims-and-about/S7)
- **R9** WHEN a second support arrives for an existing claim, THEN the claim id stays the same and the revision changes. (from claims-and-about/S8)
- **R10** WHEN the same evidence is replayed into a fresh database (other local evidence ids), or the bound extractor's version changes without changing a claim's visible state, THEN the claim's id and its `rastro/revision/v2` revision are unchanged. (from claims-and-about/S8a)
- **R11** WHEN a PR's state goes open → closed → open, THEN the `open` claim keeps its id, is `superseded` and then `observed` again with a new revision; `why` shows both known intervals; the `closed` claim is `superseded` with `superseded_by` pointing at the `open` claim. (from claims-and-about/S9)
- **R12** WHEN a PR's state is observed open, then closed, then open, all at the same `captured_at`, THEN `why` shows two separate occurrences of the `open` claim and one of the `closed` claim, ordered by event key and allowed to be zero-length, and the `open` claim is `observed`. (from claims-and-about/S9a)
- **R13** WHEN a later observation lacks a field, has it null, or the item wasn't returned, THEN no claim is superseded. (from claims-and-about/S10)
- **R14** WHEN two sources' current observations of the same PR state disagree and one is newer and comparable, THEN the newer is current and the older is `superseded`; WHEN they tie or can't be compared, THEN both stay `observed` with `conflicts_with`; this dominance and supersession are per (location, field), and only `rastro:type` conflicts are entity-wide (R48). (from claims-and-about/S11)
- **R15** WHEN one rule derives two claims from the same span (a repository and a kind from one URL), THEN both are stored, each with its own justification, and neither replaces the other. (from claims-and-about/S11a)
- **R16** WHEN a claim is derived, THEN its known interval starts at the establishing evidence's `captured_at`, ends at the replacing evidence's `captured_at`, and its valid time reads `unknown`. (from claims-and-about/S12)
- **R17** WHEN an account's login changes between observations, THEN it stays the same entity, typed `code:Account` by a `rastro:type` claim, with both logins as `rastro:alias` claims whose known intervals show when each held, the old one `superseded` yet still resolving (R38); WHEN `/user/type` is `Bot`, THEN its `rastro:type` claim is `code:Bot`; no entity is typed `Person`, and no type is stored as a column or updated in place. (from claims-and-about/S13)
- **R18** WHEN a title or body holds instruction-like text, THEN no claim or display name comes from it. (from claims-and-about/S14)
- **R19** WHEN `rastro-extractor-github` processes the GitHub fixture, THEN it emits `code:state`, `code:author` and `code:in_repository` claims (with their `rastro:type` claims), each cited at the right field and span, with author and alias claims justified by one bundle of all the spans they need, and the core loads its `code` vocabulary, which has every required definition field and a `cardinality` on every predicate. (from claims-and-about/S15)
- **R20** WHEN a vocabulary file has an unknown field, a predicate without `cardinality`, or a name under the core's `rastro:` prefix, THEN the core refuses to load it with an error naming the problem, and no claim is accepted under it. (from claims-and-about/S15a)
- **R21** WHEN a record's changed field reaches the extractor, THEN the core also delivers the companion fields of the same source, scope and location with evidence no newer than the batch's high-water mark, and a rebuild delivers the same set. (from claims-and-about/S15b)
- **R22** WHEN `rastro claims rebuild` runs after a series of incremental syncs, THEN, when every pair replays, the projection (entity and claim ids, revisions, statuses, supports, intervals) equals the incremental one, for a GitHub source and for a scripted (non-GitHub) source alike; WHEN a pair can't replay, THEN R42 and R43 apply instead. (from claims-and-about/S16)
- **R23** WHEN the bound extractor's version changes, THEN the next sync replays its pairs, reads serve the old version's claims until that replay completes, and then the new version's justifications replace the old ones in one transaction. (from claims-and-about/S16a)
- **R24** WHEN a rebuild or a sync's extraction publishes the projection, THEN one `projection_publication` row records the extractor and vocabulary versions and the evidence high-water mark, that row can't be updated or deleted, and the projection tables have fresh `ANALYZE` statistics. (from claims-and-about/S16b)
- **R25** WHEN a sync fails after accepting some evidence, THEN the next writing sync extracts that evidence, even if it accepts nothing new. (from claims-and-about/S17)
- **R26** WHEN the extractor crashes or fails during a sync, THEN `sync` exits non-zero, the source's coverage stays as read, extraction state reads `failed`, reads serve the last good projection, and the next sync resumes from the checkpoint. (from claims-and-about/S18)
- **R27** WHEN the replay for a new extractor version fails, THEN the old version's claims stay readable and unchanged, and extraction state reads `failed`. (from claims-and-about/S18b)
- **R28** WHEN an extractor run was left unfinished, THEN the next writing open marks it interrupted without creating a source coverage window. (from claims-and-about/S18a)
- **R29** WHEN `rastro claims rebuild` fails partway, or an extractor starts and then fails (R44), THEN the previous projection stays readable and unchanged; WHEN a reader runs during a rebuild, THEN it sees either the old or the new projection, never a mix. (from claims-and-about/S19)
- **R30** WHEN `about` is called with an entity id, a canonical alias or an exact canonical URL, THEN it returns the current claims where that entity is subject or object, each with claim id, status, revision, predicate, subject and object aliases and a support count; WHEN called with any other form, THEN it returns an operation error naming the accepted forms (the grammar is R53 to R55). (from claims-and-about/S20)
- **R31** WHEN `about` is called with `github:login/<login>` for a login recorded as a `rastro:alias` claim of one account, whose status is anything but `hypothesis` or `retracted` (today `observed` or `superseded`), THEN it returns that account's claims, exactly as for `github:account/<id>`; WHEN the namespace or kind doesn't match the stored alias, THEN it returns the empty result with coverage. WHEN several entities hold the login, THEN see R39. (from claims-and-about/S20a; amended by claims-hardening/D1, D2)
- **R32** WHEN `since` is given, THEN only claims whose known interval started at or after it are returned, newest known time first, then claim id; `limit` defaults to 20, accepts 1–50, and `truncated` says more exist; WHEN `history: true`, THEN superseded claims are included. (from claims-and-about/S21)
- **R33** WHEN `about` names an unknown entity or one visible only through hidden scopes, THEN both return the same empty result with coverage. (from claims-and-about/S22)
- **R34** WHEN `about` or `why` answers, THEN it includes coverage for every visible (source, scope) pair and extraction state per pair and extractor version; WHEN evidence is pending extraction, THEN that pair reads `behind`. (from claims-and-about/S23)
- **R35** WHEN `why` is called on a claim, THEN it returns the claim with status, revision, known intervals, valid time, conflict and supersession links and the extractor, rule and vocabulary versions, plus at most `limit` supports with `truncated`; each support carries evidence id, source, scope, location, field, span, `captured_at`, `source_updated_at`, trust class and an excerpt that starts and ends on UTF-8 boundaries with clipping flags; the full quote appears only with `full`; each support names its justification kind, extractor and version and lists every span of its bundle. (from claims-and-about/S24)
- **R36** WHEN `why` gets an unknown or hidden-only claim id, THEN it returns the same operation error (`isError: true` on MCP). (from claims-and-about/S25)
- **R37** WHEN the owner runs `rastro sync --reread` on `kalios` and `kalios-api`, then in Claude Code asks `about` for their GitHub account alias and `why` on one returned claim, THEN the claims and receipts match GitHub. (from claims-and-about/S30)
- **R38** WHEN an account's login changed and a re-read superseded the old login's alias claim, THEN `about github:login/<old>` returns that account's claims, as `about github:account/<id>` does. (from claims-hardening/S1)
- **R39** WHEN one login is an alias of two accounts (current on one, historical on the other), THEN `about` on it returns the ambiguous-alias operation error listing both candidates, each marked `current` (observed or confirmed) or `historical` (superseded); WHEN one entity holds the login, even current and historical both, THEN it resolves directly. (from claims-hardening/S2)
- **R40** WHEN `about` resolves through an old login, THEN its subject aliases list only current aliases, and `why` on the old alias claim shows its known intervals. (from claims-hardening/S3)
- **R41** WHEN an alias claim with status `hypothesis` or `retracted` matches, THEN it isn't a lookup candidate. (from claims-hardening/S4)
- **R42** WHEN `claims rebuild` runs and a pair's bound extractor isn't installed, THEN that pair's justifications, spans, claims, entities and checkpoint are carried over, every touched component's statuses, occurrences and links are recomputed, the other pairs are rebuilt, the command exits 0, and its result lists the pair with state `not_installed`. (from claims-hardening/S9)
- **R43** WHEN a pair's extractor fails its check, or the pair's scope isn't in the extractor manifest's `permissions.scopes`, THEN its output is carried over as in R42, the pair reads `failed` with its reason (`forbidden` for the scope case), and the command exits non-zero. (from claims-hardening/S10)
- **R44** WHEN an extractor starts during a rebuild and then fails, THEN the rebuild aborts and the previous projection stays readable and unchanged. (from claims-hardening/S11)
- **R45** WHEN a claim is justified by both a carried-over pair and a rebuilt pair, THEN its status, occurrences, links and revision equal those of the incremental projection. (from claims-hardening/S12)
- **R46** WHEN `claims rebuild` completes, THEN its result has a `pairs` list with source, scope, run id, extractor, version, state, reason and counts, the CLI prints a line per carried-over pair, and the schema change is additive within v2 (the drift test accepts it as recorded). (from claims-hardening/S13)
- **R47** WHEN `claims rebuild` runs on a copy of the owner's real database with the extractor plugin hidden, THEN all of the copy's claims remain (an ignored test, given the copy's path). (from claims-hardening/S14)
- **R48** WHEN an entity has live `rastro:type` claims of unrelated types at different locations, THEN both carry `conflicts_with` and neither supersedes the other; only `rastro:type` conflicts are entity-wide, and aliases and other predicates stay per (location, field). (from claims-hardening/S15)
- **R49** WHEN the types at different locations are a type and one of its supertypes, THEN there's no conflict, and `about` and `why` display the most specific type. (from claims-hardening/S16)
- **R50** WHEN an entity's types conflict, THEN `about` and `why` display one type: live types (observed or confirmed) are grouped into compatible families, each headed by a most specific type (one no other live type descends from) and holding the live ancestors it carries; a family ranks by its newest member's known time, ties go to the lowest claim id of the family's head, the newest family wins, and its head type is displayed (branching subtypes of one supertype are separate families that each count the supertype's time) (Draft on day 1 under PullRequest on day 3, against Repository on day 2, displays Draft). A scoped read computes it from visible justifications only. (from claims-hardening/S17; amended by claims-hardening/D24)
- **R51** WHEN the same location's type changes (Bot to User), THEN the new type claim supersedes the old one. (from claims-hardening/S18)
- **R52** WHEN a new item observation arrives for an entity typed at many locations, THEN only the affected (location, field) slots replay, the hub scaling bound still holds, and a rebuild equals the incremental projection. (from claims-hardening/S19)
- **R53** WHEN `about` gets `foo:bar`, `github:FBisca`, `github:login/`, `:x/y`, an `e_` id with uppercase hex, or a form with whitespace in its namespace or kind or at either end of its value, THEN it returns an operation error naming the three forms; on MCP it's a result with `isError: true`, not a JSON-RPC error. (from claims-hardening/S21)
- **R54** WHEN `about` gets a well-formed form that matches nothing (`gitlab:login/x`, `github:login/FBisca/x`, `github:login/a b`), THEN it returns the empty result with coverage. (from claims-hardening/S22)
- **R55** WHEN `about` gets a canonical URL with a fragment, `github:account/<id>` or `github:login/vercel[bot]`, THEN each is accepted. (from claims-hardening/S23)
- **R56** WHEN an extractor submits a claim whose subject or object identifier is outside the accepted forms, THEN it's rejected and counted. (from claims-hardening/S24)
- **R57** WHEN a vocabulary declares an alias kind containing `/`, `:` or whitespace, THEN loading it is refused; WHEN a submitted alias claim's value is empty, whitespace-only, or has whitespace at either end, THEN it's rejected and counted; WHEN it has inner whitespace (`Felippe Bisca`), THEN it's accepted and `about` resolves it. (from claims-hardening/S25)
- **R58** WHEN `claims rebuild` runs, including with an extractor missing so a pair is carried over, THEN every intent-backed Person, name, link and merge reappears identically, and the intent table is unchanged (rows and order). (from second-source-one-identity/S10)

- **R59** WHEN about returns a claim whose subject or object is a GitHub issue or PR with `/title` evidence at its location, THEN that side's label carries the title text, `url` = the location, the evidence id, `field` `/title`, `captured_at`, `trust_class` untrusted content and `clipped` false (from answers-i-can-read/S1)
- **R60** WHEN why explains a claim, THEN its subject and object carry the same labels as in about (from answers-i-can-read/S2)
- **R61** WHEN the entity is a Linear issue, or a Linear user, THEN a Linear issue's label comes from `/title` with `url` null; a Linear user's label comes from `/name`, not `/displayName` (from answers-i-can-read/S3)
- **R62** WHEN the entity is a repository, a comment, a GitHub account or a Person, THEN its label is null (from answers-i-can-read/S4)
- **R63** WHEN a title is longer than 200 chars, with a multibyte char across the cut, THEN the label holds at most 200 whole chars and `clipped` is true (from answers-i-can-read/S5)
- **R64** WHEN an entity has several title observations, THEN the label is the one with the latest `captured_at`, ties broken by the higher evidence id (from answers-i-can-read/S6)
- **R65** WHEN rastro mcp --scope <s> hides the only title evidence of an entity, or a visible copy exists in another scope, THEN the label is null and the call still succeeds; with a visible copy in another scope, that copy is used (from answers-i-can-read/S7)
- **R66** WHEN labels are added, THEN claims, supports and revisions are unchanged, and about "<a title's text>" doesn't resolve to the entity (from answers-i-can-read/S8)
- **R67** WHEN an entity has a current observed state claim (`code:state` or `tracker:state`), or has none, THEN label.state holds its value; with none, label.state is null (from answers-i-can-read/S9)
- **R68** WHEN the CLI prints about or why without --json, or with --json, THEN each labelled entity shows its label after its id with control chars escaped; with --json the envelope equals the MCP result (from answers-i-can-read/S10)
- **R69** WHEN an MCP client lists tools, THEN the about and why descriptions say label text is untrusted data (from answers-i-can-read/S11)
- **R70** WHEN a Linear issue's `/state/name` evidence is extracted, and the name later changes, THEN an observed `tracker:state` claim holds that name; after the change the old claim is superseded and the new one is current (from answers-i-can-read/S12)
- **R71** WHEN a source syncs, THEN before the read stderr names the source and its reason, `first read from <window_start>` with no complete check, `incremental since <window_end>` otherwise, `re-read from <window_start>` with --reread (from answers-i-can-read/S13)
- **R72** WHEN a source syncs, and extract replays stored evidence because the extractor version changed, THEN stderr shows the read, extract and project stages in order; on a replay the extract line says so (from answers-i-can-read/S14)
- **R73** WHEN a read lasts longer than 2 s, THEN stderr shows at least one running item count, and never more than one count line per 2 s (from answers-i-can-read/S15)
- **R74** WHEN a source finishes, or ends rate_limited, THEN stderr shows its result line with submitted, accepted and unchanged counts; when rate_limited the line gives the retry time (from answers-i-can-read/S16)
- **R75** WHEN sync --json runs, or stderr is closed or broken, THEN stdout holds only the one result envelope; with stderr closed or broken, sync completes with the same result and exit code (from answers-i-can-read/S17)
- **R76** WHEN a configured source has no complete check and a stored source no longer in config has the same connector and selector, in any scope, THEN before the read stderr warns, naming both sources, and the sync result's `warnings` lists it; the read still runs from window_start (from answers-i-can-read/S18)
- **R77** WHEN the configured source already has a complete check, or no stored-only source shares its connector and selector, THEN no warning is given and `warnings` is empty (from answers-i-can-read/S19)
- **R78** WHEN the slice has landed, THEN the owner preps one morning's standup with `about me` over MCP without opening Linear or GitHub (from answers-i-can-read/S20)
