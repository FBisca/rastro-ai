## Requirements
- **R1** WHEN `rastro identity me` runs, THEN a `rastro:person/<id>` entity typed `rastro:Person` exists and `about me` resolves to it; WHEN it runs again, THEN it returns the same Person and records no new intent. (from second-source-one-identity/S3)
- **R2** WHEN `rastro identity person create --name "Ana Silva"` runs twice, THEN two distinct Persons exist and `about "rastro:name/Ana Silva"` returns the ambiguous-alias error listing both. (from second-source-one-identity/S4)
- **R3** WHEN the owner links `github:login/<x>` to a Person, THEN `about github:login/<x>` shows `rastro:held_by` that Person, and `why` on the link shows status `observed` with an `owner_intent` justification giving the intent's id, time and issuer. (from second-source-one-identity/S5)
- **R4** WHEN the owner undoes that link, THEN the `held_by` claim is gone, a cannot-link for the pair is recorded, and `rastro identity history <entity>` lists the link, undo and cannot-link in acceptance order. (from second-source-one-identity/S6)
- **R5** WHEN the owner merges two Persons, THEN `about` on either shows the claims of both Persons' accounts with equivalent claims grouped; WHEN the merge is undone, THEN they separate and a cannot-link is recorded. (from second-source-one-identity/S7)
- **R6** WHEN an intent is invalid (a `held_by` from a Person, a merge of two accounts or of an entity with itself, a target that doesn't exist, an undo of a missing or already-undone intent), THEN it's refused with an operation error naming the reason, and no intent is stored. (from second-source-one-identity/S8)
- **R7** WHEN an intent is issued from a context whose scopes can't see its target, THEN it's refused (storage seam). (from second-source-one-identity/S9)
- **R8** WHEN an intent is written after a scoped read was cached, THEN the next scoped read reflects it. (from second-source-one-identity/S11)
- **R9** WHEN the GitHub connector syncs, THEN evidence records the token owner's account, its verified emails (unverified ones excluded) and each author account's profile name, and `about` on the token owner's account shows its `github:email/…` aliases. (from second-source-one-identity/S12)
- **R10** WHEN the GitHub token can't read `/user/emails`, THEN coverage says the emails couldn't be read, and the sync still succeeds. (from second-source-one-identity/S13)
- **R11** WHEN `me` exists and a sync records the GitHub token owner, THEN that account is `held_by` `me` with a token-owner justification, with no owner command. (from second-source-one-identity/S14)
- **R12** WHEN account B has a verified email equal (ASCII case-folded) to a verified email of an account already linked to Person P, over an overlapping interval, THEN B is `held_by` P, justified by both email observations; WHEN no linked account has that email, THEN no link and no Person is created. (from second-source-one-identity/S15)
- **R13** WHEN the equal emails were observed only over non-overlapping intervals, THEN no link exists. (from second-source-one-identity/S16)
- **R14** WHEN a matching email belongs to a Linear guest, THEN no automatic link is made. (from second-source-one-identity/S16a)
- **R15** WHEN a cannot-link exists between B and P (directly or through a `same_as` chain), THEN the automatic link isn't made; WHEN the owner then links them explicitly, THEN the link exists. (from second-source-one-identity/S17)
- **R16** WHEN the email is no longer observed on B, THEN the link's interval closes and `about` shows it as historical. (from second-source-one-identity/S18)
- **R17** WHEN `me` exists and a Linear sync records the API key's user, THEN that Linear account is `held_by` `me` with a token-owner justification. (from second-source-one-identity/S19)
- **R18** WHEN a Linear source syncs against the scripted API, THEN users become `linear:user/<uuid>` entities typed `tracker:Account` with `email` and `name` aliases and their active state, the viewer's involved issues become `tracker:Issue` entities with creator and assignee claims, and `rastro search` finds issue text with citations. (from second-source-one-identity/S20)
- **R19** WHEN a Linear user is deactivated, THEN its account shows it, and its existing links remain, marked deactivated. (from second-source-one-identity/S21)
- **R20** WHEN no Linear API key is available, THEN the pair fails with an auth failure shown in coverage, and the key never appears in the database or config. (from second-source-one-identity/S22)
- **R21** WHEN a GitHub account and a Linear account have the same full name after case and accent folding and aren't linked to one Person, THEN `rastro identity candidates` lists the pair with reason `same name`. (from second-source-one-identity/S23)
- **R22** WHEN a Linear email's local part equals a GitHub login, THEN the pair is listed with reason `email matches login`. (from second-source-one-identity/S24)
- **R23** WHEN the owner answers yes to a candidate, THEN both accounts are `held_by` one Person (the existing one, or a new one named from the candidate) and the pair no longer appears. (from second-source-one-identity/S25)
- **R24** WHEN the owner answers no, THEN a cannot-link is recorded, the pair never appears again, including after `claims rebuild`. (from second-source-one-identity/S26)
- **R25** WHEN a pair is within one namespace or includes a `code:Bot`, THEN it's never a candidate. (from second-source-one-identity/S27)
- **R26** WHEN `about me` runs with linked GitHub and Linear accounts, THEN the result lists the Person, each linked account with its reason, and the accounts' claims, each citing its own account, with equivalent claims grouped and counted once toward `limit`. (from second-source-one-identity/S28)
- **R27** WHEN `about` names an account linked to a Person, THEN the result includes `rastro:held_by` that Person. (from second-source-one-identity/S29)
- **R28** WHEN a scoped read can't see any of a Person's linked accounts, THEN `about` on that Person equals the unknown-entity answer; `about me` in any scope shows only the visible accounts and claims. (from second-source-one-identity/S30)
- **R29** WHEN the random scope-set oracle runs with intents and automatic links, THEN each scoped answer, including links visible only where both ends are, equals a per-scope rebuild. (from second-source-one-identity/S31)
- **R30** WHEN `about me` would exceed the work budget, THEN it fails with the budget error instead of a partial answer. (from second-source-one-identity/S33)
- **R31** WHEN the ignored live test runs on a copy of the owner's database after the owner synced `svc-platform` and Linear and ran `rastro identity me`, THEN `about me` lists the owner's GitHub and Linear accounts, and `rastro identity candidates` returns without error. (from second-source-one-identity/S34)
- **R32** WHEN a link, owner or automatic, names an account side whose type no vocabulary declares an account (a `code:PullRequest`, a `code:Repository`), THEN it's refused (an owner link with an operation error naming the reason; an automatic link is never made), while `code:Account` and `tracker:Account` link as before. (from second-source-one-identity/S35)
- **R33** WHEN the owner undoes a link or a merge, or names a Person again, THEN the undone claim (or the older name) stays as `superseded` with its interval closed at that time, `about` shows it as historical, and the older name still resolves to the Person. (from second-source-one-identity/S36)
- **R34** WHEN the owner undoes a Person's newer name, THEN the older name shows a gap: closed when the newer name was given and open again from the undo. (from second-source-one-identity/S36a)
- **R35** WHEN an intent is issued, THEN its `issuer_context` lists the issuing surface's configured scopes, and `rastro identity history` shows them. (from second-source-one-identity/S37)
- **R36** WHEN a Linear sync reads an app (integration) user, THEN it's typed `tracker:Bot`, never `tracker:Account`, and a link to it is refused. (from second-source-one-identity/S38)
- **R37** WHEN two cannot-linked accounts each qualify for an automatic link to one Person over non-overlapping intervals, THEN each holds that Person over its own interval, and over any overlap neither does. (from second-source-one-identity/S40)
